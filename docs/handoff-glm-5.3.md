## 子 Agent 纪律

- 启动规格采用“有效指定优先，未指定使用宿主默认”。包括模型、推理强度、Agent 类型、运行环境、前后台方式、并发和深度等选项。
- 不强制子 Agent 使用 GLM-5.3，不擅自注入固定模型、资源档位或嵌套上限；本提示的目标模型不等于对子 Agent 的显式选型。
- 用户本次指定优先于项目配置，项目配置优先于团队配置。不可用指定不能静默替换；未公开的宿主默认参数不能编造。
- 每次委派明确目标、事实、责任范围、保持项、约束与授权、预期产物、证据、依赖和是否允许继续委派。
- 普通执行者不自行递归；获准的任务所有者仍受宿主和预算限制。无嵌套能力时由上层接管或串行推进。
- 子任务结束先待验收。父 Agent 检查实际差异与证据，整合后重新验证。缺少必需分片不能算完成。
- 不让多个执行者同时驱动共享应用实例；旧任务停止状态未知时，不重新分配同一写入目标。

## 必须保持的产品边界

1. 工程指导可以读取和分析；“先讨论”“不要修改”时不修改任务文件。
2. 能力可替换，但输入、产物和证据要求保持稳定。不得把某个第三方 Skill 的模板或发布行为写成通用前提。
3. 用户可以跳过非强制检查，必须如实记录；项目强制门禁不由普通对话覆盖。检查通过不自动授予合并或部署权限。
4. 功能地图描述真实入口、前提、操作和成功条件。文档漂移、验证工具缺口与产品缺陷分别处理，不能改预期来掩盖回归。
5. Evals 比较真实行为。候选隔离，评分标准先定义，原始任务验收要求正常提供；预算耗尽停止，不为追分无限循环。
6. 无真实工具、独立上下文或证据时报告缺口，不以自述替代验证。无法验证比较条件一致时，不将结果差异单独归因于 Skill。
7. 核心工程内容共用。Codex 先验收；Cursor、Claude Code 未验证前只列计划支持。
8. 不自动安装陌生 Skill、修改全局副本、覆盖用户配置、执行生产部署或自动合并。团队默认 Skill 的候选更新需按维护流程处理。

## 验证与交付

先读每个子 Issue 的验收条件，再选择最小实现。分层运行 Skill 格式、引用、脚本和目标行为检查；最后真实调用 Codex 并运行 CLI 样例及最小评测。Markdown 存在不等于能力可用，静态检查不代替宿主调用或产品操作。

当前宿主无法完成 Codex 实测时，完成其余工作并明确列出未验证项及复验步骤；不要关闭要求真实验证的 Issue，也不要声称完整支持。不要为了赶进度把关键检查改成宽松条件。

每个子 Issue 使用可审阅的独立提交，提交与 PR 描述使用中文。根据实际工作流创建相应 PR，关联子 Issue；依赖 PR 未合并时明确基线和合并顺序，不重复计入文档差异。发布 PR 前检查差异和相关验证结果。不要擅自合并 PR 或关闭未满足验收的 Issue。

交付报告包含：实现范围、文件与 PR、实际运行的检查和证据、未验证与失败项、剩余风险及下一步。保持总 Issue 的子任务状态准确；骨架完成与全面兼容分别报告。
