## 主要缺口

### 1. 目标和验收标准不明确

目前只有项目名称，没有说明：

- 这个 Demo 要演示什么能力
- 面向谁
- 用户如何使用
- 预期输入和输出是什么
- 什么结果算完成

这是最大的缺口。现在直接选 Python、Node 或其他技术栈开始搭代码，容易先做出一个“能运行但不代表正确目标”的样例。

### 2. 没有最小可运行闭环

缺少从入口到用户可观察结果的完整路径：

```text
安装/准备环境 → 执行入口 → 获得预期输出
```

目前 README 也没有安装、运行和示例输出说明。

### 3. 没有可重复验证机制

缺少：

- 至少一个行为测试或冒烟测试
- 明确的测试命令
- 干净环境中的验证步骤

因此未来即使添加代码，也无法可靠判断它是否完成。

### 4. 工程基础设施尚未建立

根据实际需要，后续可能需要补充：

- 语言和依赖声明
- `.gitignore`
- nimo 项目配置
- CI

其中 `.nimo/project.yaml` **不是实现 Demo 功能的绝对前置条件**；如果项目要使用 nimo 的项目级能力绑定、入口或验证约定，再加入它更合适，不建议仅为了“文件齐全”而提前堆配置。

### 5. 版本历史还不能支持有效回溯

只有 `init` 一条提交，尚未形成“规格 → 实现 → 测试”的可追溯历史。这个问题优先级低于明确目标和实现闭环，不应现在为了提交数量而人为拆分。

## 优先动作

### 第一优先：先确定一页以内的产品规格

在开始写代码前，先讨论并确定以下内容：

1. Demo 的一句话目标
2. 用户或调用方是谁
3. 最小输入
4. 最小输出或可观察效果
5. 采用的技术栈
6. 运行环境
7. 至少一个成功场景
8. 至少一个失败或边界场景
9. 是否需要 nimo 项目配置、CI 和外部依赖

这是当前最短路径，因为现有仓库没有足够信息支持合理的架构选择。

### 第二优先：实现一条最小垂直切片

规格确定后，不要先搭完整框架，而是只实现：

```text
一个入口 + 一个核心行为 + 一条 README 运行命令
```

先证明 Demo 能被运行并产生目标结果，再补充结构。

### 第三优先：立即为核心行为加测试

至少覆盖：

- 一个正常成功场景
- 一个关键无效输入或边界场景

测试应验证用户可观察行为，而不是只验证内部实现细节。

### 第四优先：补齐与实际技术栈匹配的工程配置

只添加确实需要的内容：

- 依赖/构建文件
- `.gitignore`
- README 的安装、运行、测试说明
- 若使用 nimo 项目级能力，再添加 `.nimo/project.yaml`
- 若项目需要持续集成，再添加最小 CI

### 第五优先：在干净环境中做一次端到端验证

从全新克隆或干净目录开始，按 README 完成：

```text
准备依赖 → 运行 Demo → 运行测试
```

最后再形成语义清晰的提交，而不是以“提交数量”作为完成目标。

## 完成条件

我建议把 Demo 的完成定义为以下行为条件，而不是固定文件数量：

### 必须满足

- README 说明 Demo 的目标、适用场景和预期结果。
- 存在一个真实可执行入口。
- 新使用者能根据 README 在干净环境中运行它。
- 入口执行能够产生与规格一致的可观察结果。
- 至少有一个成功场景测试。
- 至少有一个重要错误或边界场景测试。
- README 明确给出测试命令。
- 安装、运行、测试命令在目标环境中均成功。
- 工作区没有因实现产生的未提交业务变更。
- 项目不依赖未文档化的本地文件、全局状态或人工步骤。

### 按需满足

- 如果 nimo 需要管理项目级能力、入口或验证规则：`.nimo/project.yaml` 存在且内容有效。
- 如果项目有外部依赖：依赖文件能够在干净环境中完成安装。
- 如果项目需要多人协作或持续交付：CI 能执行至少一次安装、测试和入口校验。
- 如果项目有发布或演示要求：补充示例输入、示例输出和已知限制。

### 建议的最终验收表

```text
[ ] Demo 目标和用户场景已确认
[ ] 技术栈和运行环境已确认
[ ] 最小入口可以执行
[ ] README 可指导首次使用者运行
[ ] 成功场景测试通过
[ ] 关键错误/边界场景测试通过
[ ] 干净环境端到端验证通过
[ ] 按需配置已补齐
[ ] Git 工作区干净
```

**结论：** 现在最应该推进的不是选框架或写代码，而是先把 Demo 的目标和最小可观察行为定下来。规格一旦明确，下一步应直接做一个可运行、可测试的最小闭环。
