# Nimo 设计原则

本文定义 Nimo 的七项核心设计原则，是这些原则的唯一权威版本。README 只保留摘要；如后续文档与本文冲突，应优先校准本文或明确说明适用边界，而不是让多份原则各自演化。

这七项原则约束的是 Nimo 自身的架构与演进方式。仓库中现有的工程原则、Playbook 和 Skill 属于执行层方法，不与这里的设计原则混为一层。

## 1. 约束结果，不约束路径

Nimo 应优先定义任务必须满足的工程不变量：目标、边界、交付物、验收标准、证据要求以及不可越过的安全约束；具体如何拆解、排序、选工具、并行、重试和回退，应尽量留给 Agent 自主决策。

这不是“完全不约束过程”。当执行顺序本身关系到安全、数据一致性、兼容契约或不可逆风险时，顺序就是工程不变量，应被明确约束。判断标准不是“过程能不能写出来”，而是“这个过程约束是否真的影响结果正确性或风险边界”。

因此，Nimo 应控制工程结果和边界，而不是把 Agent 固化成工作流执行器。

## 2. 稳定原则，弹性方法

Principle 定义长期稳定的工程判断标准，回答“什么是对的”；Playbook 描述在当前模型、工具和团队能力下通常有效的做法，回答“通常怎么做”。

二者生命周期不同：Principle 应谨慎变化，Playbook 应允许随着模型能力、工具能力和实践证据持续调整、裁剪甚至退役。不能因为某个阶段的模型需要详细步骤，就把这些步骤永久固化成 Nimo 的架构约束。

必要的安全检查、合规要求和不可绕过的验收条件不属于“可随意裁剪的方法”，它们应进入明确的边界或门禁。

## 3. 能力定义与实现解耦

Nimo 应用 Capability 描述稳定的能力合同，而不是把工程方法绑定到某个具体 Skill、CLI、MCP、模型或宿主。

一个 Capability 至少应能说明：需要什么输入、产生什么输出、有哪些前置条件和副作用、必须提供什么证据，以及怎样判断实现满足合同。具体实现可以由不同 Provider 提供，例如 Skill、CLI、MCP、Agent 或宿主原生能力。

替换实现时，变化的是 Provider，不应连带改变任务目标、工程要求和验收标准。只有当能力合同本身发生变化时，才应该修改上层方法。

## 4. 上下文按需装配

Nimo 的 Harness 不应通过不断堆叠提示词来获得可靠性，而应围绕当前任务动态装配最小充分上下文。

一次有效装配通常来自任务意图、团队与项目原则、相关知识、可用 Capability、运行环境能力和本次任务约束。Principle、Knowledge、Playbook、Skill 等内容应按任务相关性选择，而不是默认全部注入。

当多个来源发生冲突时，应显式解析冲突和优先级，不能依赖提示词拼接顺序偶然决定结果。上下文越多并不天然越可靠；无关、重复或互相冲突的上下文会增加推理负担并降低可预测性。

因此，目标是最小有效 Harness，而不是最大上下文。

## 5. 决策指导、执行边界与结果门禁分层

Nimo 需要把三个不同问题分开：

- **Harness：应该怎么做。** 由 Principle、Playbook、Task Contract、上下文和能力选择等组成，负责影响 Agent 的判断与计划。
- **Runtime：允许做什么。** 由宿主或执行环境提供沙箱、文件和网络访问、工具权限、凭证范围、资源和时间限制等，负责约束 Agent 的执行能力。
- **Gate：做到什么程度才能继续。** 基于交付物、证据、测试、评审、安全检查、人工审批等条件决定任务是否可以进入下一状态。

三者都可能形成约束，但约束对象不同：Harness 约束决策，Runtime 约束能力边界，Gate 约束状态迁移。

Nimo 可以定义 Gate 的条件、需要的证据以及判定方法，但如果某个门禁必须做到“不可绕过”，最终强制执行应落在具备控制权的系统中，例如 CI、仓库保护、审批系统或发布平台。只写在提示词里的“必须通过”不是强制门禁；Agent 自己停止执行，也不能替代外部强制控制。

一个典型控制链路是：

```text
Harness：应该怎么做
        ↓
Runtime：允许做什么
        ↓
Agent 执行
        ↓
Artifact + Evidence
        ↓
Gate：是否允许继续
        ↓
下一阶段 / 修复 / 重试 / 阻断
```

## 6. 证据决定完成

任务完成不能建立在 Agent 的自我声明上。可信完成至少需要把交付物、证据、验证结果和门禁判定关联起来。

证据应尽可能满足四个要求：

1. 与当前交付物或版本直接对应，而不是引用旧结果；
2. 能证明用户可观察行为或明确的验收条件，而不是只证明“代码能编译”；
3. 跳过、失败、受阻和未验证必须显式记录，不能被包装成通过；
4. 在成本合理时应可复跑、可审查、可追溯。

因此，`Artifact → Evidence → Verification → Gate` 是完成判定链。没有足够证据时，正确状态是“未验证”或“受阻”，而不是“完成”。

## 7. Harness 本身持续演进

Nimo 不应假设当前的 Principle、Playbook、Capability、Knowledge 或 Skill 一定正确。Harness 本身也必须成为可观测、可评测和可改进的工程对象。

改进闭环应尽量基于真实任务和可检查证据：

```text
Harness
  ↓
Execute
  ↓
Trace + Artifact + Evidence
  ↓
Eval
  ↓
定位问题
  ↓
调整 Harness
  ↓
回归验证
```

Eval 不只评价“Agent 做得好不好”，还应帮助区分问题来自哪里：上下文是否装配错误、Playbook 是否形成干扰、Capability 是否缺失、Provider 是否不可靠、Principle 是否冲突、Gate 是否过松或过严。

Harness 的变化也应有证据支持。模型能力增强后，应主动检查哪些步骤可以删除、哪些 Playbook 可以简化或退役，而不是让历史约束不断累积。

## 七句话摘要

1. **约束结果，不约束路径** —— 明确工程不变量，保留 Agent 自主规划空间。
2. **稳定原则，弹性方法** —— Principle 长期稳定，Playbook 随模型和实践演进。
3. **能力与实现解耦** —— Capability 定义合同，Skill、CLI、MCP 和其他 Provider 可替换。
4. **上下文按需装配** —— 构建最小有效 Harness，不把所有知识和规则一次性灌给模型。
5. **决策、边界、门禁分层** —— Harness 管“应该怎么做”，Runtime 管“允许做什么”，Gate 管“做到什么程度才能继续”。
6. **证据决定完成** —— Artifact、Evidence、Verification 和 Gate 共同构成可信完成判定。
7. **Harness 持续演进** —— 用真实任务、轨迹和 Eval 持续优化原则、方法、能力与知识。

## 与仓库其他“原则”的关系

Nimo 仓库中的工程原则解决具体研发行为问题，例如先质疑前提、优先最小改动、验证真实行为等；它们是执行层的默认工程纪律。

本文七项设计原则位于更高一层，约束 Nimo 如何设计这些工程原则、Playbook、Capability、验证和门禁。两者的关系是：

```text
七大设计原则
    ↓ 约束 Nimo 的架构与演进
工程原则 / Playbook / Capability / Gate 定义
    ↓ 指导具体任务
Agent 执行与验证
```
