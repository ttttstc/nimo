# 对抗式多模型评审

为用户配置的每个评审模型各派一名独立评审者，对代码变更进行对抗式审查。所有评审者拿到相同的任务意图、代码上下文和评审标准。有效信号来自模型之间真实的推理差异，而不是给同一模型分配不同人设。

交付物是一份综合裁决。**不要自动应用修改。**

## 委派机制

评审者使用宿主提供的独立子 Agent／独立上下文，只读执行。宿主没有独立上下文时，由主 Agent 亲自执行评审并明确说明降级；这种情况不能称为独立审查。宿主只有一种模型时，可以使用同模型的独立上下文，但必须说明缺少跨模型多样性，此时“多模型一致”不能作为置信度信号。

全部委派遵守 [委派纪律](../nimo-mode/references/delegation.md)。

## 步骤 1：确定评审范围

从当前上下文确定要审查的内容：

- 用户指定文件或 diff 时，直接使用。
- 当前处于功能分支时，使用相对正确基线分支的完整 diff。
- 用户引用最近完成的工作时，收集相关变更和必要的周边文件。

评审输入必须包含足够上下文，让评审者能理解变更，而不只是孤立代码片段。

## 步骤 2：明确变更意图

派出评审者之前，先用一段话说明这次变更要实现什么。依据按优先级包括：

- 用户当前要求
- PR 描述
- 提交信息
- 代码本身

评审者判断的是“实现是否满足意图、有没有破坏约束”，不是自行重写产品目标。意图确实无法从已有信息确定时，再向用户确认。

## 步骤 3：并行派出评审者

为用户配置的评审模型各派一名评审者；未配置时使用宿主实际可用模型。能使用多模型时优先不同模型家族。宿主支持并行时一次性派出；不支持时按委派纪律顺序执行并保持上下文隔离。

每名评审者拿到：

1. 步骤 2 的任务意图
2. diff 或文件内容及必要上下文
3. [评审标准](references/rubric.md)
4. [代码质量视角](references/code-quality-review.md)
5. [评审者提示词模板](references/reviewer-prompt.md)

配置模型在当前宿主不可用时，从实际可用模型中选择最接近的等价物，优先同家族较高推理档位。记录替换，不因模型名称问题阻塞评审。若配置表示“继承当前模型”，直接使用父 Agent 模型，不把它当作错误配置。

## 步骤 4：综合发现

结果返回后建立统一问题集：

1. 解析全部发现。
2. 合并实际指向同一问题的重复描述。
3. 标记被两个以上不同模型独立发现的问题，这类发现通常信号更高。
4. 保留单模型发现，但降低默认权重，仍然逐条判断。
5. 记录模型之间明确的分歧。

跨模型一致只是信号，不自动等于正确；主 Agent 仍然必须检查实际代码和上下文。

## 步骤 5：负责人裁决

主 Agent 是最终负责人，不是中立汇总器。阅读 [负责人裁决框架](references/lead-judgment.md)，结合完整任务上下文判断每条发现。

将发现分为：

- **处理**：给定真实目标，确实影响正确性、安全或可维护性，应阻塞当前交付。
- **考虑**：问题真实，但现在处理是否值得仍取决于成本和收益。
- **记录**：观察有效，但当前不可操作、影响较低或依赖后续上下文。
- **驳回**：判断错误、吹毛求疵或缺少关键上下文。

每条发现都写明提出它的模型、归类和一行理由。

## 输出结构

### 意图

步骤 2 的任务意图。

### 评审者

逐个列出模型和发现数量。

### 处理

必须解决的问题、提出模型和阻塞理由。

### 考虑

值得进一步判断的问题及其成本收益。

### 记录

有效但低优先级的观察。

### 驳回

被否定的问题及简短原因。

### 一致性图谱

说明不同模型在哪些问题上独立收敛、在哪些地方分歧，以及这种一致或分歧对最终判断意味着什么。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。本 Skill 只评审，不自动修改代码。只读、方案或停止要求优先，步骤不扩大授权。交付具体结论、证据、未确认项及原因。
