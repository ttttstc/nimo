# 评审标准

用相关的视角评审。不是每个视角都适用于每个变更。用判断力。

## 正确性

代码是否真的做了意图说它该做的事？

- 边缘情况：空输入、nil／undefined、边界值、并发访问
- 错误处理：错误被捕获、传播，还是被静默吞掉？
- 差一错误、类型强转、整数溢出、字符串编码
- 状态管理：竞态条件、过期闭包、悬空引用
- 快乐路径走得通吗？异常路径走得通吗？
- 幂等性：这个操作跑两遍会怎样？上一次运行中途崩溃后会怎样？答案是"取决于留下了什么状态"时，就缺一步对账。
- 并发：多个执行者能碰同一份可变状态（文件、分支、共享数据）时，访问是结构性地串行（锁、顺序阶段、独占所有权），还是靠守不住的约定？

发现潜在 bug 时，追执行路径。不要只标记"这里可能是 nil"。展示让它是 nil 的调用链。

## 根因 vs 症状

代码修的是真正的问题，还是在给症状打补丁？

回答这个问题常常要看变更文件之外。读周边代码（调用者、被调用者、类型定义、兄弟模块），理解变更所处的架构。用你可用的工具去探索（按文件名找、按符号搜、读实现），追调用链，读类型，先理解代码为什么存在，再判断变更是否改在了正确的层。

- 掩盖更深层不变量被破坏的守卫子句
- 掩盖坏契约的重试逻辑
- 压下建模错误的类型强转
- 看到 workaround 就问：为什么需要它？正确的修复长什么样？
- 改在模块 A、本该改模块 B 契约的修复
- 用说明代替结构：如果修复是一条"别做 X"的注释或一个要人记住的约定，问它能不能变成让错误做法做不出来的类型约束、lint 规则或运行时检查

## 结构完整性

代码是否良好地嵌入了它所属的系统？

- 边界纪律：验证在系统边界做，还是散落在业务逻辑里？数据在哪里进入系统就在哪里验证一次，之后在内部信任它。
- 抽象层级：代码是否把高层编排和底层细节混在一起？
- 耦合：这个变更是否引入了让未来变更更难的依赖？
- 数据模型契合度：数据结构是否匹配实际访问模式？正确的结构让下游代码显然；错误的处处跟你较劲。
- 外挂 vs 融入：变更是钉在既有设计上的补丁，还是读起来像设计本来就考虑到了它？如果新需求从第一天就被知道，代码会长这样吗？
- 双轨遗留路径：变更是不是引入新 API 又留着旧的？没有外部消费者时，同一波里迁移调用者并删掉旧路径。不要留下会变成永久性的兼容层。

不要因为简单代码缺少抽象而扣分。过早抽象比重复更糟。

## 验证

从阅读中能看出这段代码能跑吗？

- 有测试吗？测的是行为还是实现细节？
- 有能抓住回归的断言／不变量吗？
- 这是 bug 修复：有为这个 bug 的测试吗？
- 触及集成边界：完整路径被测试了吗？
- 查真东西，不查代理：代码用文件 mtime 或缓存状态检查存活，而不是读实际值，就是验证缺口。
- 委派或异步工作：代码验证实际产出物，还是信任自我报告和摘要？

## 复杂度预算

复杂度是否配得上代码完成的事？

- 不损失正确性或清晰度就能更简单的代码
- 只服务一个调用点的抽象
- 为不存在的场景准备的配置或参数化
- 死代码、无用导入、残留参数
- 过度工程：没有当前调用者的"以防万一"代码路径
- 为已不再需要的过渡稳定而保留的废弃兼容路径。迁移完成就删脚手架。
- 用户体验配得上复杂度吗？每个功能、控件、选项都应挣得自己的位置。半成品功能比没有更糟。

更简单更好，除非简单是错的。三行重复胜过过早抽象。

## 安全

只标记能实际在代码中追到路径的安全问题。"这可能是注入向量"而不展示输入路径没有用。

- 用户输入未净化就流向危险汇点（SQL、shell、eval、innerHTML）
- 新端点的认证／授权缺口
- 代码、日志或错误信息里的秘密
- 安全关键路径上的 TOCTOU（检查时／使用时竞态）
