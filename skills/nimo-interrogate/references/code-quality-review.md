# 代码质量评审

每名评审者在评审标准之外应用这个代码质量视角。它是一套严格标准，聚焦实现质量、可维护性、抽象质量与代码库健康。

最重要的是对代码结构抱有雄心。不要只找局部清理。主动搜索"代码柔道"招法：保持行为不变、同时让实现戏剧性变简单、变小、变直接、变优雅的重构。

## 核心提示词

从这个基线出发：

> 对当前分支的变更做一次深度代码质量审计。
> 重新思考如何组织／实现这些变更，在不影响行为的前提下切实提升代码质量。
> 致力于改进抽象、模块化，减少面条代码，提升简洁性与可读性。
> 要有雄心：如果存在一条涉及重构部分代码库的明确路径能显著改进实现，就冲。
> 极度彻底、极度严谨。三思而后行。

## 维度

每个维度只陈述一次。应用相关的那些。

0. **对结构性简化抱有雄心。** 不要停在"这里可以更干净一点"。寻找让整个分支、helper、模式、条件或层消失的重新定式。假设"代码柔道"招法通常存在：它更有效地利用既有架构，让变更戏剧性变简单。能把复杂度删掉而不是挪来挪去时，用力推。

1. **不允许 PR 在没有非常强理由的情况下把一个文件从 1000 行以下推到 1000 行以上。** 把它当作强气味。优先提取 helper、子组件或模块。diff 跨过这条线时，问代码是否应该先分解。只有当结果文件保持清晰组织、且存在令人信服的结构性理由时才豁免。

2. **不允许既有代码里长面条。** 对新的临时条件、散落的特例、插进无关流程的一次性分支保持怀疑。把"随机位置上的怪 if"当设计问题，不是风格瑕疵。优先把逻辑推进专门的 helper、状态机或模块，而不是纠缠既有路径。

3. **偏向清理设计，而不是接受能跑的代码。** 行为可以不变而结构显著更干净时，推更干净的版本。优先删除活动部件的简化，而不是把同样的复杂度摊开的重构。

4. **优先直接、无聊、可维护的代码，而不是 hacky 或魔法代码。** 把脆弱、临时、"魔法"行为当问题。对隐藏简单数据形状假设的泛型机制保持怀疑。标记没有换来清晰度的薄抽象、身份包装器或透传 helper。

5. **在影响可维护性时紧盯类型与边界清洁。** 质疑不必要的可选性、`unknown`、`any` 或 cast 密集的代码——明明可以有更清晰的类型边界。优先显式类型化模型而不是松散形状的临时对象。一个分支靠静默回退粉饰不清晰的不变量时，问边界是否应该显式化。

6. **把逻辑留在权威层，复用既有 helper。** 点出泄漏进共享路径的功能逻辑，或穿过 API 泄漏的实现细节。优先既有的权威工具而不是定制一次性代码。把代码推向正确的包、服务或模块，而不是把漂移正常化。

7. **当更干净的结构显而易见时，把不必要的串行编排与非原子更新当设计气味。** 无关的工作没有理由被串行时，问是否应该并行。相关更新可能让状态停在半应用时，推更原子的结构。不要过度关注微优化，但要标记让代码更脆弱的可避免编排复杂度。

## 输出期望

优先报告结构性代码质量退化与错过的简化，其次面条与分支复杂度，其次边界、类型与文件规模问题，最后较小的模块化与可读性问题。存在更大结构性问题时，不要用低价值琐碎淹没评审。宁要少数高信念的评论，不要一长串化妆式笔记。

## 批准门槛

不要仅因行为看起来正确就批准。以下情形视为推定性阻塞，除非作者能给出辩解：PR 保留了大量附带复杂度而一个柔道招法就能删掉它；把文件从 1000 行以下推到 1000 行以上；添加纠缠既有流程的临时分支；把功能检查散布到共享代码里；添加不必要的抽象、包装器或 cast 密集的契约；或在存在明确权威归属时复制既有 helper 或把逻辑放错层。作者给不出辩解时，留下显式、可执行的反馈，并推更干净的分解。

## 评审语气

对质量直接、严肃、挑剔。不要粗鲁，但不要把重大可维护性问题软化成温和建议。代码正在让代码库变得更乱，就直说。实现错过了一个显著的戏剧性简化，也直说。真实问题是结构性的时候，不要满足于"也许把这个改个名"。
