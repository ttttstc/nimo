# 项目知识维护（nimo-knowledge-maintain）

本 Skill 把项目真实状态编译成 Agent 可低成本消费的项目知识，并持续保持它与代码、配置、接口、测试和运行方式一致。知识正文始终留在用户通过 `knowledge` 配置指定的位置；nimo 不要求迁移到 `.nimo`。`.nimo` 只保存配置和维护状态。

先完整读取 [知识维护契约](../nimo-mode/references/knowledge.md)、[配置规则](../nimo-mode/references/configuration.md) 与 [本地工具契约](../nimo-mode/references/tools.md)。用户的只读、停止、范围限制和不修改要求优先。

## 结果

一次维护必须明确属于以下一种模式：

- **基线生成**：已配置知识目标，但其中没有足够的可复用项目事实；从仓库真实资产建立第一版知识基线。
- **增量刷新**：存在可信维护基线，只重新理解自基线以来变化的事实来源及其影响知识。
- **全量刷新**：用户明确要求，或维护基线不可用、历史不可追溯、项目结构发生大规模迁移，重新核对整个知识范围。

模式是执行策略，不要求用户记住。默认优先增量；“全量刷新”表示重新核对，不表示无条件重写全部文档。

## 写入边界

1. 只写当前有效团队配置 `.nimo/nimo.yaml` 与个人配置 `~/.nimo/nimo.yaml` 中登记的 `knowledge` 目标；新增知识路径先交给 [configure-nimo](../configure-nimo/SKILL.md)，本 Skill 不偷偷选择 `docs/` 或创建 `.nimo/knowledge`。个人目标同样需要用户当前写入授权；配置可见不等于自动授权修改。
2. 已有文件默认为 `user-managed`：只改能够明确定位、且已被项目证据证明发生变化的事实片段；不统一文风、不重排全文、不顺手修无关内容。
3. 本 Skill 在已登记目录中创建的知识文件记为 `managed-by-nimo`：可随项目事实持续整理，但仍遵守最小修改和证据约束。
4. 代码、配置、测试、接口定义、流水线、运行结果和已有文档可以是事实证据源；成为证据源不授予写权限。
5. 规划、未实现需求、聊天猜测、Agent 主观评价和无法证明的历史原因不写成当前项目事实。

## 知识结构

目录型知识目标优先形成三层渐进式结构：

1. **概览（Overview）**：高度压缩地回答项目定位、核心领域、关键模块、主要运行链路、重要约束以及下一跳知识入口。控制为冷启动 Agent 可快速读取的体量。
2. **索引（Index）**：覆盖全仓重要知识域；每个条目至少包含“这个领域是什么 / 详细知识在哪里 / 必要时回到哪些事实证据”。索引是查询第一跳，不做只有文件名的目录清单。
3. **知识页（Knowledge Pages）**：架构、领域、接口、数据、运行、开发等稳定事实；关键主张带源码、配置、测试或其他可定位证据。

具体文件名与拆分根据项目现状决定；已有良好文档应复用，不为了统一模板复制一套平行知识。单文件 `knowledge` 目标只能在该文件内组织“概览 / 索引 / 主题事实”，不得未经配置在旁边创建兄弟文件。

知识结构必须支持逐层读取：`Overview → Index → Page → 原始项目证据`。后续 Agent 能从前两层定位少量相关知识时，不应重新扫描全仓。

## 流程

0. **确认授权与目标。** 读取团队/个人 `knowledge` 配置并解析真实路径，形成当前有效目标集合。没有配置时停止写入，提示用户先通过 `configure-nimo` 或手工配置指定知识位置。远程宿主无法访问本机路径时报告受阻，不猜测替代位置。
1. **判定模式。** 通过 `knowledge-state.mjs` 读取维护状态（不存在时按无可信基线处理）并取得当前仓库版本。没有足够项目事实时用基线生成；维护基线可追溯且变更范围可收敛时用增量；用户明确全量或基线失效时用全量。状态文件缺失只能导致降级核对，不能让已有知识失效。
2. **盘点知识目标并核对指纹。** 区分目录/单文件、`user-managed`/`managed-by-nimo`、当前概览/索引/知识页以及已有事实覆盖。若存在维护状态，先用 `knowledge-state.mjs check` 比较当前知识文件和保存的 `contentHash`；`CHANGED`、`MISSING`、`UNTRACKED` 都进入本次候选，不能仅凭源码无变化跳过。无法可靠比对时扩大核对范围。
3. **建立事实地图。** 从仓库入口、代码结构、接口/Schema、配置、测试、构建/运行说明和必要版本历史识别稳定项目事实。优先结构与用户可观察契约，不做逐文件源码摘要。把事实关联到具体证据源和受影响知识目标。
4. **编译或刷新知识。** 先更新具体知识页，再根据页面新增/删除/职责变化更新 Index；只有顶层领域、架构、核心流程或项目定位变化时才更新 Overview。已有事实仍正确就保持不动。
5. **维护导航质量。** 清理死链接、错误摘要、重复入口和孤儿知识；关键知识页应能从 Overview/Index 到达，重要跨域关系有必要的交叉链接。索引摘要必须足以让 Agent 在不知道文件名时选择正确下一跳。
6. **原子记录维护状态。** 首次维护先调用 `knowledge-state.mjs init`。知识正文全部写入并针对当前 `projectVersion` 读回验证后，计算该次实际验证字节的 SHA-256 作为 `expectedContentHash`；随后调用 `knowledge-state.mjs update`，传 `expectedRevision`、当前项目版本、维护时间以及每个实际知识文件的绝对路径、所有权、`verifiedRevision = projectVersion`、`expectedContentHash` 和证据来源。工具在持锁期间重新读取文件并重算哈希；若内容在验证后发生变化则以 `CONTENT_CHANGED` 阻断，不把未验证的新内容记为基线。任一目标的 `verifiedRevision` 与 `projectVersion` 不一致时不得推进全局 `lastMaintainedRevision`。
7. **验证可消费性。** 用至少一个与项目核心领域相关的冷启动查询做路由检查：只读 Overview/Index，确认能定位到少量正确知识页；再抽查知识页到原始证据的链路。若仍必须无差别扫描全仓才能定位，索引不算完成。
8. **交付。** 报告模式、改动知识、证据范围、未覆盖项、维护版本和路由检查结果。除非当前授权包含提交/PR，不自动创建提交或 PR。

## 增量规则

- 增量候选由两部分取并集：**知识目标自身指纹变化** 与 **最近可信 `lastMaintainedRevision` 到当前版本的事实源变化**。任一侧命中都必须重新判断；文件变化只是“可能影响”，不能直接判定事实漂移。
- `lastMaintainedRevision` 只有在本次完整快照中所有目标都验证到同一 `projectVersion` 后才能推进；因此不会领先于任一目标的验证版本。
- 已有 `source → knowledge` 映射时只核对受影响目标；出现新核心模块、公共接口、Schema、配置契约、运行链路或构建方式时，即使旧映射中没有，也要判断是否形成新的知识事实和索引入口。
- 基线不可达、历史重写、映射大面积失真、目标指纹无法可靠比对或结构迁移到无法可靠收敛时，升级为更广或全量核对并说明原因。
- 删除项目能力时同步处理正文、Index 和必要的 Overview；不能只删底层页面留下幽灵入口。

## 项目事实标准

适合进入知识：系统结构、模块职责、调用和状态关系、公共接口、数据结构、配置契约、构建/测试/运行方式、外部系统依赖、已落地且有证据的架构决定。

不直接进入知识：临时任务进度、未来计划、未实现需求、主观质量评价、无证据设计意图、仅由聊天推断的事实。

关键事实至少能回溯到路径、符号、配置、测试、接口或运行证据。知识可以使用简短“来源”段落；精确 hash/revision 等放维护状态，避免正文被机器元数据淹没。

## 完成标准

- 基线场景：从无有效项目事实到具备可查询 Overview/Index/Pages（或单文件等价结构），且事实有证据。
- 增量场景：知识目标自身变化和事实源变化都参与候选选择，只更新真实受影响知识；无理由全文重写为失败。
- 全量场景：全部登记知识被重新核对，仍正确的内容保持稳定。
- 用户已有文档：只改确认的项目事实，不改观点、规划、风格和无关内容。
- 查询效率：冷启动 Agent 能通过高压缩概览和索引定位知识，不需要先遍历全仓。
- 维护状态：知识正文和状态均完成读回核对；状态只作增量缓存，不能成为知识真相源。
- 未配置知识路径、关键证据不可访问或写入边界不明确时报告受阻，不自行扩大范围。

本 Skill 不替代 [nimo-knowledge-audit](../nimo-knowledge-audit/SKILL.md)。审计负责只读判断是否漂移；维护负责在明确授权下恢复知识正确性。
