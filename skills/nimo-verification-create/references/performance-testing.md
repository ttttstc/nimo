# 构筑性能用例与测量协议

仅在 [Create 的性能范围](../SKILL.md#0-确定建设范围与性能授权) 已获显式确认，或用户明确进入性能优化流程时读取。普通测试建设不预加载本文。本文规定资产内容；真实执行、证据和结果判定由 [nimo-verify](../../nimo-verify/SKILL.md) 负责，不创建第二套结果状态。

## 先固定用户场景

从当前授权范围内的核心操作选场景。新项目先定义预期，功能具备真实入口后再生成可执行资产，不要求所有功能开发前先写完性能脚本。

每条用例在运行前固定以下内容，复用项目已有 harness、数据和功能断言。缺少决定性输入时记录缺口，不填造数字。

| 内容 | 必须记录 |
|---|---|
| 场景与来源 | 用户操作、对应功能条目、性能授权来源、相关验收要求 |
| 起点与终点 | 真实用户动作开始，到结果真正可用；同时验证正确结果和副作用 |
| 工作负载 | 数据规模、历史状态、并发、冷／热缓存、预热与重置方法 |
| 指标与预期 | 主指标、单位、越大或越小越好、统计口径、绝对预算或退化阈值及其依据 |
| 运行环境 | 产物版本与工作区差异、构建方式、机器、运行时、视口、网络、CPU 条件和外部依赖 |
| 测量命令 | 可重复命令、采样次数与理由、A/B 顺序、超时和失败样本处理、资源所有权 |
| 正确性护栏 | 必须保持的行为、数据、输出、视觉或内容；引用已有回归用例 |
| 证据 | 原始样本、成功与失败数、trace、协议版本、基线来源与适用环境 |

终点不是骨架屏、DOM 出现或按钮看起来可点。编辑器要验证输入被接收且框架接管后未丢失；导入要验证结果可读且内容正确；API 要验证响应语义，不能用空结果换速度。首个可用结果与全部完成有不同价值时分别记录，不混成一个指标。

## 区分预算、基线与退化阈值

- **预算**来自用户要求或已确认的产品约束，不能默认设为“快一半”。
- **基线**来自真实测量。新项目没有旧版时先记录首个有效基线，不编造 A/B 对比或改善百分比。
- **退化阈值**根据已确认预算、重复性和环境噪声确定。基线超预算不代表预算应上调。

没有预算时可以交付测量资产与基线，但只能证明测量可运行，不能宣称性能达标。资产构筑完成和产品性能验收是两件事。采样不足、口径不一致或证据不足时保留不可判定；有效测量违反已固定预期时保留失败。

## 保持对照可比

1. 使用真实操作面与明确的构建产物。Web 开发服务器、生产构建、桌面 exe 和线上环境分别记录，不相互替代。
2. 冻结用例、负载、统计方法和环境。前后使用相同条件；口径变化后同时重测两版，旧数据只作历史记录。
3. 冷启动与热启动分组，不混合样本。冷缓存需说明重置的是浏览器、进程、服务端还是 OS 缓存；新浏览器上下文不能证明服务端也已冷启动。
4. 最终耗时对比在同一时段串行交替测 A/B，并轮换顺序，例如 AB、BA。隔离端口、profile 和数据，避免后台实例活动污染另一版本。机器上不要同时跑构建、压测或其他资源密集任务。不能隔离时先记录限制，不能宣称无噪声改善。
5. 根据场景选定统计口径与采样量，报告原始样本和离散程度。少量样本的 p95 不能冒充稳定尾延迟结论。Web 示例可从每版 10 次、p50/p75 开始探查，但这不是充分性保证，也不是所有操作面的默认值。
6. 保留超时、错误和失败样本及顺序；不得只对成功样本算出漂亮分位数就判通过。运行前约定失败规则，区分产品失败和环境无效测量；缺失、非有限值、有效样本不足应明确报错或不可判定，脚本不能以成功退出掩盖检查未完成。

Web 测量需固定视口与设备档，网络限速覆盖所有被测请求，包括本地和同源资源。若只给外部 CDN 限速，同源托管会产生假收益。LCP、资源字节和长任务都要说明采集窗口、支持能力与缺失项；跨域不可见数据不能当作零成本。

本机网络、代理或网关可影响线上观测。对照站可帮助排查共同噪声，但不能仅凭两个站点耗时接近就断言服务器无问题。实验室、单机线上实测、真实用户遥测分别报告；没有真实用户数据就写没有，不用 Lighthouse 分数替代。

CLI、API、桌面或库按实际入口测量，记录进程启动、请求边界或调用边界。吞吐与并发测试同时检查错误率和资源成本。只增加并发、减少结果或把成本移到首次使用，不能算无代价的改善。

## 证明指标有效

先重复运行不变版本，确认测量波动；再用已知慢路径、受控负载或可逆扰动检查灵敏度。用例分不出预期的快慢，就修测量方法，不开始追逐数字。

请求数、传输字节、渲染次数、布局次数、CPU 指令数可以是候选代理指标，先验证在当前环境和负载下是否稳定。耗时和长任务总时长不是确定性计数，工具标志也不能自动保证确定性。

代理指标需用成对证据证明它的变化对应真实用户结果改善，写明机制和适用边界。一次或两次同向变化不足以保证长期有效。关联尚未证明时只用于诊断，不单独作为性能通过依据；负载、架构或运行时变化后重新校准。代理变好但用户耗时未改善，不宣称提速。

## 正确性先于速度

在优化前，先由 `nimo-verify` 证明相关正确性护栏可运行。根据改动选择必要护栏，不要求每个项目机械套用全部项目：

- 静态外壳或初始化交接：持续输入、中文输入、已有草稿、状态恢复，接管后不丢字、不覆盖旧内容。
- 延迟加载：每个受影响入口首次使用、重复使用、并发调用与加载失败恢复，不能只看首屏。
- 缓存或增量渲染：失效条件、状态隔离和输出正确性；已有黄金样本可复用。只在契约要求字节一致时逐字节比较，否则比较业务等价结果。
- 视觉或布局变化：覆盖相关视口与阶段。整体 CLS 良好不能替代指定区域不抖动的要求；截图之外按场景保留 trace 或录屏。
- 内容站：需要保持的文本、链接和 SEO 字段。预览时机、动画或信息呈现改变属于体验取舍，不能只凭指标收益替用户决定。

构筑测试不会自动授权产品修复。性能改善但护栏失败时仍不能通过；发现其他瓶颈只记录，不自动扩大优化范围。

## 固化防退化检查

将用例挂在原功能条目中，复用 `.nimo/verification/scripts/`。详细协议和阈值可拆文件并链接，原始运行证据按项目约定存于忽略目录，保留验证对象与工作区差异绑定。

阈值文件至少区分场景、指标、方向、统计口径、协议版本、负载与环境档位，并引用基线证据。URL 不能作为唯一标识。检查先核实可比性和样本有效性，再比较绝对预算或相对退化限值。

**检查只读；更新阈值单独进行。** 这是文中“棘轮”的适配：确认改善后保护收益，不把一次偶然快样本永久设为上限。收紧阈值需重复证据且正确性护栏通过；吞吐等越大越好的指标应提高下限，不能统一降低数字。不能静默放宽阈值迁就失败。

环境、工作负载或测量协议变化时，由 Maintain 标记旧基线不再可比并重新校准；产品要求变化导致预算调整时需显式确认并留原因。`nimo-verify` 不写基线和阈值。CI 接线、定时测量或自动收紧只有另获对应授权才建立，不因测试资产生成而自动执行。

## 交付证据

由 `nimo-verify` 的逐场景报告给出：版本、环境、冻结协议、前后样本量与失败数、指标与变化、护栏结果、证据位置及局限。无基线、无预算和缺运行条件分别写清。多个优化有交互影响时不把每步收益简单相加。

需要用例写法时读取 [性能用例示例](performance-case-example.md)。
