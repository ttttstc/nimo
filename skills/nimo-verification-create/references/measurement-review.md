# 测量结论复核

在已经拿到性能数字、准备写进交付说明或据此做取舍时读取本文。复核只问四件事：声明的提速在算术上是否可能、限制点从哪里来、比的是配置还是实现、被计时的工作是否真的发生。用例构筑、基线、采样协议与防退化检查属于 [性能用例与测量协议](performance-testing.md)，实际运行与结果判定属于 [nimo-verify](../../nimo-verify/SKILL.md)，本文不重复。

复核针对一句已经写好的结论，例如“导出在 6 万行数据上 p50 快 30%”。四个问题检验这句话，而不是检验代码意图。先把结论写成准备发表的原句，再逐条找证据。

## 算术上限

判据：从操作计数与单次成本推算可能的最大改善，并把推导写出来。去掉占整轮 10% 的一段，整轮最多快约 11%；每秒操作数乘以单次成本不得超过可用核数；传输速率不得超过磁盘或网络带宽；节省的时间不得超过被改动部分自身的耗时。算出的上限低于声明值时，先解释差额来自哪里，再谈结果。

反例与失败信号：

- 声明的提速超过被优化部分在整轮中的耗时占比。
- 只有百分比，没有输入量、单次成本和可用资源，无法复核。
- 数字超过物理带宽或核数上限，却仍按“被测工作变快”报告。
- 换过统计口径后上限才成立，而口径变化本身没有声明。

## 命名限制点

判据：限制点从一次不用于汇报的采样运行里读出来。分分析器和跟踪器会拖慢被测工作，读限制点的运行与用于汇报的运行分开。CPU 看运行时分分析器或每进程 CPU 统计，I/O 看等待时间与系统调用计数，再把热点映射到源码位置。同时观察负载发生器：它先饱和时，测到的是负载发生器。结论里必须带限制点，例如“p50 由单核上的 JSON 解析决定”。

反例与失败信号：

- 只有数字没有限制点，或限制点是从代码读出来的猜测。
- 一次改动没有推动数字，就直接判定改动无用；先由限制点解释为什么没动。
- 限制点在负载发生器一侧，结论却写成被测系统的性能。
- 采样运行读到的限制点与生产推断不一致，却没有说明差异来源。

## 配置调优不等于实现改进

判据：两侧都按生产条件运行——发布构建、生产开关与环境变量、批量与事务设置、连接池、缓存的冷热、相同的版本与数据。任一侧跑在默认值上，比的是配置而不是实现。限制点本身是设置项时（逐行提交、调试构建、缺索引），该侧属于未调优，先调优再测，否则不给结论。无法调优时，不从该次运行选出胜者。用户要采纳其中一方时，也不能把说法收窄成“按今天的代码原样”，因为他采纳的是选项本身。

反例与失败信号：

- 声明“实现更快”，其中一侧实际是未调优的默认配置。
- 只改了配置项，却把收益报告成实现改进。
- 无法调优仍给出取舍建议，或用“代码不改”掩盖两侧条件不同。
- 一侧有索引、批量或连接池，另一侧没有，而报告只写实现差异。

## 工作量是否真的发生

判据：确认计时区间内工作确实执行——请求到达服务端、行被写入、字节被读出、结果被使用。惰性代码（无人迭代的生成器、无人等待的异步结果、被运行时丢弃的返回值）和超时都会产出“工作没有发生”的数字。检查手段是副作用计数、写入行数、读取字节、错误与非成功响应数，以及输出内容是否正确。空输入、全命中缓存、被短路的路径都会让数字变好而不改变产品。

反例与失败信号：

- 只有耗时，没有副作用或输出正确性证据。
- 失败与超时样本存在却被算进分位数，或只对成功样本计算。
- 计时区间不含被测路径：预热落在区间内、断言落在区间外、请求发往另一个实例。
- 输入为空或全部命中缓存，基准从未到达被测路径。
- 两次运行间剧烈波动仍按稳定结论汇报，未先确认是否根本没跑到被测代码。

## 复核记录

把结论与证据一起记录，让下一个人能判断可复现性：

- 原句：准备发表的那句话。
- 上限：操作计数、单次成本与推导过程。
- 限制点：来自哪次运行、用什么工具读到、对应哪段源码。
- 条件：两侧的构建、配置、数据与缓存状态。
- 工作量证据：副作用、输出正确性或错误计数。
- 不可判定项：无法确认的部分及原因。

四项中任一无法回答时，结论写成不可判定并指出缺哪一项。配置未对齐、限制点未知或工作量未确认，都不能用“没有可测差异”掩盖。
