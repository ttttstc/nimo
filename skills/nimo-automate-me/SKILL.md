# 把工作习惯沉淀成偏好

产物是一份个人偏好 Markdown，默认落在用户主目录的 `nimo/<handle>-mode.md`，再登记为个人原则。它不是包内 Skill：包只收 `nimo-*` 目录，个人偏好必须留在包外，否则安装与包检查都会失败。

## 边界

- 只写这个人的偏好。别的技能已有的内容改成路径引用，不抄进来。
- 不改包内技能定义。要改技能走 [nimo-skill-author](../nimo-skill-author/SKILL.md)。
- 落盘位置与是否落盘先问。写入是明确的授权动作，不是默认动作。

## 步骤

0. **先看有没有现成的。** 找用户主目录的 `nimo/*-mode.md`，以及项目里已约定的偏好目录。存在就确认是更新还是重来；更新只改被新证据推翻的小节，用户没反驳过的保留。
1. **采证据。** 来源三处：本次会话里用户明确纠正过的、他主动说过的偏好、他确认过的决策。宿主提供会话记录时才读，读不到就明说读不到，不假装采过；不跨项目翻别人的对话。找六类信号：回复偏好、委派习惯、验证姿势、代码与行文纪律、流程约定、元偏好（中途改技能、提新技能）。
2. **交叉核对。** 同一个信号出现两次以上才算证据；只出现一次又被打断的按噪声丢掉。来源说不清的写成「待确认」，不写进规则。
3. **结构化追问。** 一次一到两个多选问题，每问四到六个选项，先宽后窄，最后留一个自由回答。不要连问二十个。
4. **归类。** 只保留用户有非默认规则的类目：回复风格、自治程度、先理解再动手、子 agent、行文与代码纪律、审查与验证、流程、技能习惯。没有内容的类目直接不写，不强行凑对称。
5. **起草。** 写法遵循 [nimo-skill-author](../nimo-skill-author/SKILL.md)，文字过 [nimo-unslop](../nimo-unslop/SKILL.md)。祈使句用「用户」「agent」，不写作者本人的名字；每条规则都要能让执行者判断做没做到。
6. **落盘并登记。** 写进用户确认的路径，再按 [configure-nimo](../configure-nimo/SKILL.md) 登记为个人作用域下 `principles` 的 `path` 条目，读回确认生效。不复制被引用的文件，不动配置里其他条目。
7. **迭代。** 草稿给用户看，砍多余的部分。一份偏好文件不是手册。

## 反模式

- 用一次对话定型。说过一次、又被另一句推翻的，是噪声。
- 耍聪明。编比喻、写诗、复述别的技能的内容，对执行者都是成本。
- 堆小节。「沟通要清晰」不是规则；「短段落，比较选项时用表格，条目真的并列时才用列表」才是。
- 把别人维护的原则文档整段抄进来。给路径。

## 评估

偏好文件是主观产物，不套基准循环。给用户读一遍，问「像不像你」「漏了什么」。触发准确率真成了问题，才回头做 description 优化。

## 什么时候不该用

- 用户要的是任务型技能：用 [nimo-skill-author](../nimo-skill-author/SKILL.md)，不需要采矿。
- 只抓一个窄工作流，比如「我怎么写提交信息」：那是一般技能，不是偏好文件。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。交付偏好文件路径、登记结果、未确认的信号及原因。
