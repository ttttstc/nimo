# 跨会话项目协调

标识：PB18。跨会话项目协调时使用；先遵守 [Mode](../SKILL.md)。

## 适用与路由

你拥有的是项目，从来不是代码。写简报、清空队列、保持前沿绿色、做决定。适用于把整个项目交给一个常驻协调会话：跨多天、大量堆叠 PR、数十到数百个执行者，用户一天查看两次而不是每五分钟一次。单个任务推进到一个判定谓词，是 [autonomous-run](autonomous-run.md)；一次需要定制工作流的雄心运行，是 [nimo-figure-it-out](../../nimo-figure-it-out/SKILL.md)。工作超出任何单个执行者的生命周期时，路由到这里。单个执行者在会话预算内能完成的工作不是项目：实测对比中，本流程的仪式开销曾把半小时 12 个单元的工作做成只落地 1 个单元，而一个普通执行者落地了全部 12 个。低于这条线，路由到 autonomous-run。

仪式必须随项目规模伸缩。下面每个门禁都以协调者分钟计价；在廉价且高度同构的单元上，按各节自己的指引收缩仪式，而不是照价目表全付。

三条规则扛住其余一切：

- 完成是队列事件，不是中断。
- 每次启动和每次恢复都原样携带 standing orders。
- 简报就是产品。模糊的简报会安静地失败，因为执行者无法向你提问。

## 角色与放置

- **协调者（本会话）。** 本地。定框架、撰写简报、清收 inbox、拥有面向用户的报告、做判断决定。绝不编写或编辑代码：有冲突的合并、restack 和代码修改永远是任务。机械落地一个已验证单元（对执行者的提交做 fast-forward 或干净 cherry-pick 后推送）在本地 Git 代价低的仓库上属于记账，协调者可以自己做；把已完成的工作压在空闲栈主的队列后面，是让截止日期颗粒无收的做法。整个循环端到端由 Agent 驱动。执行者的启动、恢复和清收全部经宿主原生委派机制进行。状态读写经 nimo 本地工具在清收点进行——一条命令进、一行结果出，节省上下文（[保留必要上下文](../../nimo-principle-guard-the-context-window/SKILL.md)）；工具只记账，不派发、不等待、不唤醒任何东西。
- **子协调者。** 总是本地、持久、每轨道一个，且仅当项目超出单个协调者的清收能力时才设立。协调者自己清收得了的轨道不需要中间层：每多一层嵌套都要重付一遍完整的定向前言，一个阻塞中的子协调者会把它下面的执行者藏起来，而父级在空转。子协调者拥有本轨道的单元与看板、撰写其执行者的简报、启动自己的执行者与验证者（嵌套最多到第三层，嵌套派发同样携带完整任务合同）。在波次边界汇总聚合结果，绝不原样转发子报告。在途子项数量限制在单次清收能处理的规模——大约十个——按滚动窗口维持，绝不按阻塞批次维持，后者为每个批次支付最慢子项的代价。
- **执行者／验证者。** 默认使用宿主的独立执行环境（独立子 Agent／独立上下文），除非任务需要本机：真实 UI／CLI 运行时验证、读取本地会话记录、模拟器与本地 IDE 状态、只存在于本机的认证。独立执行环境读不到本地任务记录，给它们的简报要把所需内容内联进去或指向仓库内路径。优先更少、更宽的执行者；每个 worktree 或分支只有一个写入者（[先分离再串行共享写入](../../nimo-principle-separate-before-serializing-shared-state/SKILL.md)）。单元的验证者尽量运行在与执行者不同的模型上（用户配置的模型）；宿主只有单一模型时，用同模型的独立上下文并报告缺少跨模型多样性。

深度停在协调者、轨道、执行者三层。轨道分解按项目定制（构建、落地、验证是常见切法，不是规定形状）；硬编码的固定分片树试过，因过于僵化被搁置。

## 本地项目记录

在当前任务目录创建项目记录（`<task>/program/`，布局与操作见 [工具用法](../references/tools.md)）：`program.json` 是事实记录，`standing-orders.md` 保存常备指令，`inbox/` 存放完成指针，`decisions.tsv` 是决策轨迹。每条记录恰好一个写入者（one-writer state）；所有者发布事实，读取方在读取时聚合。记账用 nimo 本地工具 state.mjs 完成（`init | read | update | inbox-add | inbox-drain | status`），一条命令进、一行结果出；规范 JSON 始终可以不经工具直接阅读。

- `standing-orders.md` 是常备指令登记簿：编号行，每行一条约束（模型策略、链形状与数量、验证标准、禁止路径、升级策略）。把它原样粘贴进每一次启动与每一次恢复；指令会跨恢复衰减，每掉一条就多耗用户一轮。当你发现自己在重述某条指令时，先把它追加成一行再行动（[把重复错误变成约束](../../nimo-principle-encode-lessons-in-structure/SKILL.md)）。
- `program.json` 的 `units` 是持久的单元与 PR 事实库：每个单元一行（id、轨道、状态、分支、PR、head SHA、简报路径），行内原位更新；PR 与议题事实追加记录，不因单个事件整体重写。
- `frontier` 是计算出来的合入前沿（generation、按依赖排序的 PR 列表、当前最底部未合入项），按"链安全"一节维护。
- `verifications` 是验证台账，按"验证"一节维护，每条结论一行，以 PR 编号加 head SHA 为键。
- `inbox/` 存放完成指针，每个结果一个独立文件，同一事件标识幂等。`gates` 登记人类门禁（问题、选项、状态），完成洪峰不能冲掉门禁状态；门禁不带超时自动批准。
- `decisions.tsv` 是经 [nimo-show-me-your-work](../../nimo-show-me-your-work/SKILL.md) 保存的轨迹。
- `status` 从 `units` 与 `verifications` 在每次清收时派生，绝不手工维护；从表重新生成，而不是把事件叙事进去——手工维护的看板每次事件都被重写，最终没人读得懂。

## 简报

你写给执行者的提示词是你唯一的产品，一份潦草的简报会把潦草复利到整棵执行树上。每次启动携带全部字段；一个你填不出来的字段，就是一个你还没界定清楚的单元。

```
GOAL         一句话，结果导向，一个看不到聊天记录的陌生人也能执行
SCOPE        本单元可写的路径；不可写的路径；它独占的 worktree 或分支
CONTEXT      指向文件与 PR 的指针；本单元依赖的上游报告全文粘贴，
             因为执行者看不到兄弟单元
ACCEPTANCE   可检查的验收标准，一行一条
VERIFY       确切命令或验证路径，外加已知的坑
TIMEBOX      运行时长粗略上限；到期返回部分结论并停止，而不是硬跑下去
FORBIDDEN    不改 PR 链拓扑、不 rebase、不 force-push、不做范围外修复，
             加上单元专属禁令
REPORT       状态、分支、head SHA、PR、结论、实际运行的命令、偏差、
             建议的后续跟进
STANDING     <standing-orders.md 原文粘贴>
```

简报按单元配重。一条命令的单元把模板收缩成一段话，但仍然写明目标、范围、验证命令和报告形状；围绕两行修改搭 4KB 脚手架，写与遵守的成本都高于修改本身。能读任务目录的本地启动可以按路径引用 standing-orders 文件；独立环境的启动和每一次恢复都要原样粘贴。

子协调者简报额外携带：它的轨道边界与单元清单、启动预算（独立环境默认与本机例外清单）、清收协议，以及汇总格式（每个子项一行：名称、状态、PR、head SHA、结论；再加轨道状态与前沿增量）。

依赖不只是排序，更是上下文中继：未声明的上游上下文让执行者只能猜。字段缺失是拒启条件。每个子协调者每波抽查一份执行者简报，与被抽查的波并行进行，绝不作为挡在波前面的门禁；简报不合格就停该轨道，并修复子协调者的指令而不只是执行者——简报质量在运行后期会衰减。绝不靠在旧简报上续链来恢复；用合并后的范围全新重启。

## 步骤

打开任务清单，把下方编号步骤原样复制进去；跳过的步骤保留在清单上并标注 `skip: <原因>`。

1. **定框架。** 把完成谓词写成可计数的东西（"全部 126 个单元已合入，每个在台账中达到 unit-test-verified 或更好"）。量化范围：单元数、粗略工作量、预期的 PR 链、墙钟预算。如果一个执行者能在该预算内完成，到此为止，改跑 autonomous-run。收缩不得依赖另一份文件在场才成立：它意味着直接在当前会话内做工作、需要时用普通执行者、验证内联、随做随落地，不用下面任何记录、登记或试点机制。按预算排落地：到预算约 70% 时停止新启动，落地已验证的工作，因为完成而未落地的工作计为零。轨道按项目命名。有争议的分解或单向门，先过 [nimo-arena](../../nimo-arena/SKILL.md) 再进试点。框架只陈述一次；可逆的准备工作不必等待，直接开始。
2. **安装运行时。** 用 state.mjs 初始化 program（`init`）。经 [nimo-show-me-your-work](../../nimo-show-me-your-work/SKILL.md) 打开轨迹，在任何启动之前写好 standing orders，并从既有 PR 按平台实际 base/head 关系播种 frontier。
3. **试点。** 把一个单元推完整条路径：简报、执行者、验证、链登记、台账行、合并。试点存在的目的，是在代价还只是一个执行者而不是五十个时，证伪简报模板、验证配方和单元大小。从试点证据修正合同，然后才扇出。试点也按单元配重：在近乎同构的廉价单元构成的项目里，第一个单元就是试点，作为普通单元跑、验证命令内联，它一落地，扇出就开始。专职试点管线（独立验证者、审计门禁）属于昂贵或新颖的单元形状，不属于串行起来无物可证伪的克隆单元。
4. **扩规模。** 按 [nimo-swarm](../../nimo-swarm/SKILL.md) 的分片纪律，把执行者的滚动窗口开到在途上限，子项完成即补充；阻塞批次为每个批次支付最慢子项的代价。轨道子协调者只在超过"角色与放置"一节的单次清收阈值后设立。每次清收后重算就绪工作；把上游报告转发进下游简报；兄弟单元之间的通信只向上。抽查简报与被抽查的波并行进行，失败时停的是下一次补充，不是当前波。
5. **清收。** 在每个清收点执行下方"队列与清收"的纪律。
6. **落地。** 落地是持续的，从来不是收尾阶段：整合从第一个已验证单元开始，与其余波次并行。重型仓库上，栈主从第一波起就是常设角色，单元一通过验证就整合；本地 Git 代价低的仓库上，协调者按"角色与放置"一节自行落地已验证单元。上层链工作开始之前保持前沿绿色；以"链安全"一节为准。frontier 只在合并或收到新 head SHA 报告时推进。
7. **收尾。** 清空最终 inbox；把每个已启动的执行者对账到终止行（完成、放弃、僵尸对账）；在真实产物上确认谓词；确认每个已落地 PR 的当前 head SHA 都有台账结论；按 [nimo-show-me-your-work](../../nimo-show-me-your-work/SKILL.md) 审计轨迹（含跨模型审查；单一模型宿主按宿主合同报告缺少跨模型多样性）；把反复出现的纠正编码进 standing orders 或简报模板。项目记录原样保留；它就是事后复盘。

## 队列与清收

- 收到完成通知时，把结果指针写入 inbox（`inbox-add`：执行者、单元、状态、可选报告路径），然后回到你正在做的事。绝不内联深度审查；需要审查的完成变成一个验证单元。绝不在清收中审 diff。
- 在四个点批量清收：关键区段结束、轨道汇总、前沿监视者唤醒（按 [autonomous-run](autonomous-run.md) 的唤醒机制设监视，长时间隔心跳兜底）、人类报告之前。每批以 `inbox-drain` 开始；清收期间新到的结果留给下一批。
- 优先做完的关键区段：撰写简报、链操作、冲突决定、写门禁、更新台账或前沿。
- 每次清收给每个指针分类（已落地、需验证、失败、僵尸、噪音），把结果行写入 units 与 verifications（`update`），生成派生状态（`status`），然后一次性启动下一波；宿主不支持并行时按委派纪律串行派发。
- 每个已启动的子项在其轨道汇总时对账：已到达、已重启，或其范围被显式吸收。静默重做失踪子项的工作，会同时掩盖浪费的开支和它的结果本要堵上的覆盖缺口。
- 一次清收回合以派生状态的三行结束：各状态计数、变化内容、打开的门禁。细节在派生状态视图里；完整交付契约在检查点与收尾时适用。

## 链安全

- 前沿是计算对象，从来不是叙事。每次合并与链变更后，从明确目标列表和平台实际 base/head 关系重算 frontier——GitHub 的 base ref 会在 restack 中途漂移：按依赖排序的 PR 列表、分支名、head SHA、generation 号、最底部未合入的 PR。禁止用分支名排序推断链；拓扑修改前后更新 generation，旧 generation 的跟进结果不可用于新链。
- 每条链恰好一个栈主可以执行链操作（rebase、改 base、retarget、close），在链内串行；持有者写进 standing orders。大规模 restack 放独立执行环境跑；宿主没有独立执行环境时，由栈主在本机串行执行并控制规模，接受代价。
- 执行者永不 rebase、永不直接操作 PR 链拓扑。看护者按 [babysit](babysit.md) 跟进，每链一个，锁定一个不可变 frontier generation；他们把冲突报告给栈主，而不是自己 restack。
- PR 关闭与 retarget 只经栈主；关闭 base PR 会让上面整条链变孤儿。合并与链手术和其他单元一样，是带简报的任务。
- 一个回溯监视者跟住已合并 PR 的 revert、合后 CI 故障和无人认领的跟进。

## 验证

- 验证按单元配重。VERIFY 是单条廉价命令时，执行者自己跑并报告输出（结论标准按 [nimo-verify](../../nimo-verify/SKILL.md)），协调者抽查回执；专职验证者（尽量与执行者不同模型）属于验证昂贵、含判断或高爆炸半径的单元。一个验证者的全部产出只是重跑一条命令时，那是仪式，不是验证。
- 每条结论写入台账（`verifications`），以 PR 编号加 head SHA 为键；核对当前 PR 与 head SHA 用只读查询（`read`）。结论级别：`live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`。CI 绿是结论的输入，不是结论本身。行为类工作需要好于 `type-check-only`。`verifier-blocked` 不是通过；环境恢复后重新启动验证。`verifier-failed` 得到一个修复单元，不是一次重验证。执行者可以自报；验证者在同一键上覆盖它。新的 head SHA 使该行作废，restack 后重新验证。台账回答的是"这个验证过没有"，不是记忆，也不是会话记录（[验证真实产物](../../nimo-principle-prove-it-works/SKILL.md)）。
- 单元在落地那一刻外部化产出才算完成，绝不攒到运行结束：执行者推送它的分支，验证者写它的台账行，回执进任务记录。只存在于某台机器、机器一死就消失的工作，从来就不算做过。

## 存活与失败

- 绝不为了查看状态而恢复一个执行者；恢复会重启一个空闲执行者。只读探测：台账、units、平台 PR 状态（inspect-pr.mjs）、已推送分支、宿主提供的执行者状态界面。会话记录文件的修改时间不是存活证据。
- 无声死亡在 inbox 得到一行合成事后记录（单元、失败模式、最后证据、可选项）。证据到了就重规划；绝不等待完全静止。
- 按模式重试：配额或内存耗尽，缩小范围重启；网络中断，原样重试；工具错误，换模型重试；原因不明，重试一次。重试两次后放弃该单元，绕开它重规划。
- 数小时后归来的僵尸，先对照当前 frontier 与台账对账，然后才接受任何结果；它沉睡时世界已经移动。独有的发现经新单元打捞，绝不盲目合并。
- 当继续启动会在整棵树上制造垃圾（坏的上游产出、坏掉的验收标准、死掉的基础设施）时，在 standing orders 顶部写一行停止线；让在途工作跑完，修复原因，再清除停止线。
- 给自己的基础设施重试设与子项相同的边界。连续几次工具中止后停止重试：把终端移交写进持久记录（已完成什么、存放在哪、恢复的确切方式），结束运行。对着死掉的执行器循环重试几小时，产出不会多过一份移交。
- 宿主会话中断或重启后：本会话执行者已死，已外部化的工作（已推送分支、已写的台账行、平台上的 PR）没有死。重读 standing orders 与 units，重算 frontier，按 PR 和分支（而不是执行者 id）重新挂接仍存在的外部工作，每条轨道从其存储简报加当前状态重启一个子协调者，清收，继续。任务记录的锁按工具规则处理：仅当能证明持有进程已结束时才自动回收，否则交由当前所有者核实。

## 升级边界

- 到达用户那里，批量进状态页而不是逐条：不可逆动作（向共享分支 force-push、部署、删除、关闭他人的 PR）、任何试验都裁决不了的真正产品或偏好取舍、与观察到的现实相矛盾的常备指令、经历过一次重规划仍然是项目级死路。每项先落成 gates 记录再询问，并把工作绕开它路由。
- 永不到达用户那里：前沿微调、restack 机制、重试、CI 抖动分诊、审查线程分诊、格式修复、简报已明确禁止的范围（拒绝并继续），以及"我要不要继续"。拿不准时行动并记录；推迟是被实测过的失败模式。
- 运行中的发现只修阻塞前沿的东西。其余停进后续跟进；在这个扇出规模上，一次小范围泄漏会繁殖成没人要的 PR。

## 必要条件与停止

协调者负责合同、判断和整合，不直接代写执行者的代码。复杂度不足时退回 autonomous-run：单个执行者能在会话预算内完成的工作不是项目。宿主没有独立执行者时不伪造协调者／执行者分离：输出项目计划与已知状态，或明确改为单人执行并如实说明，不宣称完成编排验收。

单一所有者维护每条 PR 链的拓扑；队列事件只记录结果指针，不在写入共享状态时临时启动长审查。共享记录仅协调者写（one-writer state），子任务只交报告；每次派发和恢复传完整 standing-orders；先一个单元跑通（试点）再扩展滚动窗口。inbox 按批处理，每个派发最终有接受、失败、放弃或取消记录；旧任务停止未知时不得重派相同写入目标。恢复读当前记录、分支和平台状态，不从聊天时间推测存活。

不存在独立的 nimo 调度进程：协调随会话进行，跨会话靠持久记录恢复；宿主提供 event／timer／automation 时才可后台运行，否则会话结束即停止并留下恢复点。push、评论、合并、rebase 等外部动作受用户当前授权约束。

公共规则见 [宿主合同](../references/host-contract.md)、[工具用法](../references/tools.md) 和 [检查点](../references/checkpoints.md)。

## 交付

在检查点和收尾报告：完成谓词及其从 units 与台账得出的计数、各轨道各自落地的内容、前沿（PR 列表加 SHA）、结论汇总、放弃了什么及原因、等待用户的门禁（唯一的请求项）、任务记录路径与轨迹路径。数字来自表，不是叙事；附 PR 链接。另附当前产物版本、实际验证和证据、未完成项及跳过原因。流程不自动授予提交、推送、评论、合并或发布权限。
