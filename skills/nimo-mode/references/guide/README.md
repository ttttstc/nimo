# nimo 使用手册

这套手册只讲一件事：一个工程任务交给 agent 之后，从请求走到交付的全程长什么样，每一步留下什么证据。

不铺陈，不劝服。三页读完，能独立跑完第一个任务。

## 这套手册怎么读

三条路径，按现在的位置选一条。

**第一次用的人**：按顺序读 [第一次跑通一个任务](./01-first-task.md)，再读 [配方与坑](./02-recipes-and-pitfalls.md)。第一页给轨迹和决定权归属，第二页给工况对照表。读完就拿手里真实的活跑一遍，别拿玩具任务练。

**已经在用的人**：跳过第一页，直接看 [配方与坑](./02-recipes-and-pitfalls.md)。目的是把「这活该走哪条流程」变成条件反射，以及认出自己已经在犯的那几个错。

**维护 nimo 本身的人**：先看本页的概念图，再读 [入口路由表](../../SKILL.md)，最后拿 [配方与坑](./02-recipes-and-pitfalls.md) 里的坑逐条对照现有 playbook 的写法。改流程前先分清改的是 playbook 还是 principle：前者随模型与实践演进，后者要保持稳定。

各文件自述的上游基线会随时间落后。核对谁落后、落后多少：

```bash
node skills/nimo-mode/scripts/upstream-drift.mjs --upstream <pstack 仓库路径>
```

## nimo 是什么

一句话：nimo 是工程方法层。不是模型，也不是运行时。

它规定一个任务怎么推进、在哪一步停下、拿什么当交付证据。模型、上下文和工具执行都不在这一层。

## nimo 不是什么

- **不提供模型。** 用哪个模型、给多少上下文、能不能开子 agent，由宿主决定。nimo 只假设会有一个能读文件、能跑命令的 agent。
- **不提供 CI。** 它不在流水线里运行。验证是任务内的动作，验证资产落在仓库里，供下一次任务复用；跑不跑流水线是另一件事。
- **不替你决定产品。** 做什么、不做什么、先做哪个，由人拍板。nimo 只保证决定被记下来，后续执行不和它打架。

再补两条常见误会：

- 不是「自动写代码」的工具。它约束过程与证据，代码仍然由 agent 写。
- 不是可以按心情取舍的风格建议。门禁不能静默跳过；要跳过，就写原因和影响。

## 最小概念图

五层，自上而下。

- 入口 `nimo-mode`
  - 读请求，判意图：指导（只读、先讨论）还是执行
  - playbook：按请求选，一条请求对应一条流程
    - 缺陷 → bug-fix
    - 新行为 → feature
    - 保持行为的改形 → refactoring
    - 只读判断 → investigation
    - 没有匹配项 → nimo-figure-it-out 现设计一套
  - skill：每一步需要的具体能力
    - 摸清现状 → nimo-how
    - 跨边界取舍 → nimo-architect
    - 验证结果 → nimo-verify
    - 提交前清理 → nimo-deslop
    - 评审前清注释 → nimo-no-comments
  - principle：判断依据，按触发条件打开（完整索引在入口 SKILL 里）
  - 证据与验证：产物、命令输出、实际值、失败前后的差异
    - 结论只有三种：通过 / 失败 / 未验证

读法：从上往下看是「这活该怎么走」，从下往上看是「凭什么这么判」。中间任何一层被跳过，都要在任务里写下原因和影响。

## 术语表

后面两页会反复用到这几个词，先对齐一遍。

- **入口**：`nimo-mode`。唯一的统一入口，负责判意图和挑流程，不亲自干活。
- **playbook**：一条请求对应的固定流程，比如缺陷修复、新行为、结构改形。步骤可以细化，不能静默删。
- **skill**：一步流程需要的具体能力，比如理解现状、设计取舍、验证结果、清理差异。
- **principle**：判断依据，按触发条件打开。索引只给一行摘要，摘要不能代替正文。
- **门禁**：不许静默跳过的检查点。跳过要写原因和影响，验证受阻要标出来。
- **证据**：命令输出、实际读到的值、失败前后的差异、真实操作面的结果。编译通过不算证据。
- **验证资产**：落在仓库里的验证场景与脚本，供下一次任务复用，不是一次性的口头结论。

## 三句话问答

**要不要背流程？** 不用。记住「给目标和判据」，入口自己会挑。背下来的流程一旦遇到没覆盖的请求，反而容易硬套。

**能不能只要方案不动代码？** 能。说「先讨论」「不要修改」，只读优先，入口按指导处理，产出只有方案产物。

**跳过一步行不行？** 行，但要写原因和影响。强制门禁不能省；用户明确声明的跳过，单独记录在交付边界里，不能冒充通过。

## 两句话记住

1. 给目标和完成判据，不要给步骤清单。playbook 负责排序；手写的顺序通常会把步骤重排或漏掉。
2. 没验证就写未验证。检查通过不等于动作被授权，子 agent 说完成也不算数。
