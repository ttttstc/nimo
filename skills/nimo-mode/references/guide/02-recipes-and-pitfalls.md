# 配方与坑

上部分是八种工况的对照表：遇到这类请求，走哪条流程，关键动作是什么，常被误用成什么样。

下部分是十条重复出现的错误：现象、原因、正确做法。

配方是给真实请求用的，写得不那么正式。playbook 读的是意图，不是措辞。

## 配方

### 1. 偶发缺陷，本地跑不出来

- 场景：日志里能看见，一周两次，本地一次都没复现。
- playbook：[bug-fix](../../playbooks/bug-fix.md)
- 关键动作：在真实操作面制造触发条件——合成数据、收紧时序、加插桩，拿到失败证据再动代码。
- 常见误用：把「在崩溃点加个判空」当成修复；或者反过来，让用户自己跑一次复现。

### 2. 需求只说了半句

- 场景：要做「支持批量操作」，但批量多大、部分失败怎么回滚，没人说得清。
- playbook：[feature](../../playbooks/feature.md)，入口先走 nimo-grilling 把语义收干净
- 关键动作：术语、边界、验收先问清楚，再把验收条件写成能判对错的形式；范围可以小，判据不能虚。
- 常见误用：直接开工，用代码代替讨论。「批量」到底指同一个对象的多条，还是多个对象各一条，到评审才暴露。

### 3. 保持行为的改形

- 场景：把一个四百行的函数拆开，对外接口和副作用都不变。
- playbook：[refactoring](../../playbooks/refactoring.md)
- 关键动作：先固定行为基线（测试或真实操作面证据），拆完对同一基线复测；行为变了就不是重构。
- 常见误用：顺手改掉一个「看起来不对」的分支，把保持行为的改形做成了未声明的新行为。

### 4. 方案在几种结构之间摇摆

- 场景：缓存放进程内还是放共享层，两种都能自圆其说。
- playbook：[prototype](../../playbooks/prototype.md)
- 关键动作：做两三个能跑的版本并排比，用真实调用路径打分，再回 nimo-architect 定稿。
- 常见误用：拿三段文字描述当候选，比较的是措辞不是行为。

### 5. 只想知道这东西怎么跑

- 场景：接手一个没有文档的服务，先摸清请求链路。
- playbook：[investigation](../../playbooks/investigation.md)
- 关键动作：只读。机制讲 nimo-how，设计动机讲 nimo-why，两条线别混；结论挂到源码位置。
- 常见误用：调查途中「顺手」改了一行，把只读任务变成未授权的变更。

### 6. 一个指标要持续变好

- 场景：首屏从 1.8 秒降到 1.2 秒，一次改不到位。
- playbook：[hillclimb](../../playbooks/hillclimb.md)
- 关键动作：先定测量方法和次数，每次只接受一个赢的改动，前后数字都留，并说明测量限制。
- 常见误用：把一次热缓存下的数字当成结论，第二次跑就少了一半收益。

### 7. 接手别人停下的任务

- 场景：上一个人跑到一半，分支上有未提交改动，任务记录停在两天前。
- playbook：[session-pickup](../../playbooks/session-pickup.md)
- 关键动作：先读现场——任务记录、检查点、diff、验证证据；复述当前状态和下一步提议，等确认再往下走。
- 常见误用：从聊天记录的最后一句猜意图，接着往下推，把「未完成」当成「已认可」。

### 8. 给「自定义 UI 唤醒 agent」定边界

- 场景：需要一个悬浮按钮唤起 agent，但入口以后可能换成快捷键、语音或外部设备。
- playbook：[feature](../../playbooks/feature.md)，只在落地时进；定边界这步不属于任何 playbook
- 关键动作：只保留六条不变量——触发源可替换、密钥不进客户端、动作幂等、结果可回读、失败可见、权限最小。逐条写成能判真假的验收条件。
- 常见误用：为这一次的按钮写一个 skill，把「按钮」固化进方法层。下一个触发源进来，整套东西要重写。

这个工况值得单独说一句：六条不变量足够约束实现，写成一个 skill 反而是负担。方法层只在同一个判断会被反复用到时才值得固化。

## 坑

**小改动配了过重的设计流程。**
- 现象：改三行配置，先 architect 再 arena，一天出不来一个 diff。
- 原因：把「改了文件」当成「跨了边界」。
- 正确做法：按实际影响面选流程。单点、可逆、验证便宜，直接走 bug-fix 或 feature 的最短路径；设计流程留给真会锁死结构的决定。

**不该开子 agent 的时候开了。**
- 现象：读一个文件也扇出三个子 agent，回来的结论互相矛盾，还得自己重新读。
- 原因：把委派当成默认动作。
- 正确做法：需要连续上下文、或一句话能查清的事，主 agent 自己做；委派用在大范围调查、可切片的执行、需要独立视角的评审。

**验证受阻时把「没验」说成「验过」。**
- 现象：交付写「已验证」，证据是编译通过、流水线绿、或者子 agent 的自报。
- 原因：把代理信号当成结果。
- 正确做法：标未验证或受阻，写清缺的是哪个环境、哪条场景、补的条件是什么。真实操作面验证不能被编译、类型检查或子任务自报替代。

**长时运行没有前后契约。**
- 现象：跑一夜回来，不知道它做了什么，也不知道哪些决定在等自己拍板。
- 原因：只给了目标，没给完成判据、授权边界和记录方式。
- 正确做法：开跑前定完成条件、可自行决定的逆边界、不可逆动作的请示点，并要求留下决策日志；回来先读日志再读 diff。

**把 nimo 的规则当成可以讨价还价的建议。**
- 现象：跳过复现直接改，理由是这个 bug 反正是显然的。
- 原因：把门禁和写作风格建议混成一类。
- 正确做法：跳可以，但要显式声明跳过并写原因和影响；门禁不许静默省略。用户明确措辞永远优先，那不叫省略。

**改一处没查影响面。**
- 现象：函数改对了，调用方、路由、选择器或副作用跟着漂了。
- 原因：只验证直接场景。
- 正确做法：验证覆盖直接行为、关键不变量和合理影响范围；资产漂移走 nimo-verification-maintain，缺场景走 nimo-verification-create。

**把步骤清单写进请求。**
- 现象：手写「先 how 再 architect 再 arena」，结果漏了验证这一步。
- 原因：以为顺序写死更可控。
- 正确做法：给目标和约束，让 playbook 排序。只有要覆盖某个具体默认选择时，才点名 skill。

**拿一次性能数字当结论。**
- 现象：报告写提速四成，复跑只差三个点。
- 原因：单次测量、缓存没清、样本太小。
- 正确做法：先定测量方法与次数，重复跑，给区间和限制。数字进交付之前先自证一遍。

**用文档固化本该进结构的约束。**
- 现象：同一条纠正写进第三份文档，下一个 agent 照犯。
- 原因：文档不改变行为，读不读得到全看运气。
- 正确做法：先架构，再类型，再点名的 lint 与测试，文档放最后；固化本身走 nimo-correct。

**复现交给用户。**
- 现象：「你在本地跑一下，看能不能复现。」
- 原因：把「不可达」当成了「不可为」。
- 正确做法：主 agent 驱动插桩和合成触发条件，先把控制面推到极限；确实够不到，再记录受阻，而不是把活推回去。
