# 解释这个数字

一个测出来的数字，是关于某个系统的主张。在相信它、上报它、按它做决定之前，先找出是什么限制了它，再排除它其实测的是另一件事。

## 适用

你手上有一个刚跑出来的数字，而且接下来要做下面任一件事：

- 写进 PR 描述、报告或给用户的回复
- 拿它当优化有效、回归可接受的证据
- 按它排序、选方案、决定继续还是收手

反过来，只是跑了一次看趋势、不打算对外声称任何结论时，不必走全套，但「为什么不是两倍」这一问仍然值得问。

## 为什么存在

跑坏了一次，照样会打印出一个很像样的数字。失败的请求、跳过工作的缓存、根本没执行到的代码、留了默认设置的那一侧、跑一次的噪声——这些都会产出看上去正常的结果。

更常见的是：数字对了，理解错了。说不出「为什么它没有两倍好」，就说明你不知道自己测的是什么；这时它只是碰巧落在了一个能接受的区间里。

## 模式

三问，缺一个就不能把数字交付出去。

**一、问「为什么不是两倍」。** 点名限制这个结果的资源或代码路径：核数、锁、磁盘、网络，或者压测器自己。来源必须是 profile 或运行时的系统计数，再映射回源码里的那几行。读代码猜出来的不算 limiter——那是假设，不是观测。

**二、列出这个数字还可能是别的什么，逐条用证据排除。** 常见候选：

- 有一部分请求失败了，样本只统计了成功的
- 缓存命中，或工作被跳过，实际没做
- 只有一侧被调优，比较本身不公平
- run-to-run 噪声大于效应
- 改进只在小到端到端看不见的那一部分

排除不了的那一条，就写进结论的适用范围，不要省略。

**三、证据跟着数字走。** 跑了几次、spread 多大、limiter 是谁，写进笔记或链接到产物。只留一个孤零零的百分比，等于把判断权交给读者去猜。

## 与相邻原则的分工

[prove-it-works](../nimo-principle-prove-it-works/SKILL.md) 查的是「输出是不是真的」。本条查的是「你测出来的这个数，是不是你以为的那件事」。两者都要做，顺序上先 prove-it-works，再解释数字。

性能数字仍要走 [性能用例与测量协议](../nimo-verification-create/references/performance-testing.md) 的全流程；eval 结果同样对每个 trial 问一遍上面三问。数字已经写进交付说明、要复核它对不对时，用 [测量结论复核](../nimo-verification-create/references/measurement-review.md) 逐条检验。

## 应用证据

判为跳过的信号，出现任一条就说明数字还没到能交付的程度：

- 证据里没有 run 次数，也没有 spread
- 没有点名的 limiter，或 limiter 是从代码读出来的
- 省下的时间大于被优化部分本来耗时的总量
- 「为什么不是两倍」没有任何一行答案

## 决策例子

同事报了「快了 40%」。你问：谁在限制它？答不上来。再问：对照组的缓存是冷的还是热的？答：没记录。这两条没有，40% 只能当线索，不能当结论——按线索继续查，得出带 limiter 与 spread 的数字再上 PR。
