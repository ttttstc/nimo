# 验证当前任务的真实用户结果

"能编译"不是证据。对着真实产物和真实操作面验证，不对代理指标——编译、类型检查、内部方法调用或子任务自报都不能替代用户实际结果。

本 Skill 是 Nimo Verification 体系的**唯一执行语义**：`nimo-verification-create` 负责建立／补齐验证资产，`nimo-verification-maintain` 负责维护资产；两者需要实际运行时统一调用本 Skill，不各自维护另一套启动、驱动、证据、清理和 PASS／FAIL 规则。

Task Audit 也不执行验证。对于 Mode 判定需要 Audit 的任务，本 Skill 负责把真实执行后的逐场景结果、证据和当前 Artifact Version交给调用方写入 `.nimo/tasks/<task-id>/audit.md`；`audit.mjs` 只记账和校验自洽，不能替代本 Skill 的行为判断。

验证结论只证明其绑定的当前产物版本。验证完成后，只要待交付代码发生语义变化，原结论不再证明新版本；交付前确认最后一次语义代码变化早于最后一次有效 Final Verify，顺序相反就必须重新验证。

## 验证范围：当前任务优先

默认不做全项目回归。验证范围围绕**当前任务**收敛，至少包含：

1. **全部验收场景**：来自 Task Contract、Task Audit Contract、用户明确要求、已固定规格或缺陷原始复现；每个场景都必须得到独立结果，不能用另一个相近场景代替。
2. **直接行为**：本次新增或修改的用户可见行为。
3. **关键不变量**：改动必须继续保持的权限、状态、数据一致性、兼容性或其他核心约束。
4. **合理影响范围**：根据调用关系、共享状态、公共接口和变更位置识别出的最小相关回归，不因“项目还有很多没测的功能”自动扩成全量测试。

项目整体 Verification Coverage 可以不完整，但本次任务的验收覆盖不能含糊。与本次任务无关的历史未覆盖区域记录为项目验证债务，不阻塞当前结论。

## 步骤

1. **固定当前产物与验收场景。** 记录当前产物版本、工作区差异标识、Task Contract／Task Audit／用户要求中的全部验收场景和相关操作面。需要 Task Audit 时先核对 Audit Contract 与当前目标一致；不一致不能一边按旧 Audit 验证一边宣称新需求已覆盖。没有形式化 Contract 时，从用户请求、规格和已确认行为中提炼可检查场景；无法确定且会改变 PASS／FAIL 的产品取舍才视为输入缺口，不自行发明预期。
2. **建立场景到验证资产的映射。** 优先读 `.nimo/verification/SKILL.md` 与相关功能条目，为每个验收场景找到具体驱动路径。若某个必要场景没有可执行验证资产，转 [nimo-verification-create](../nimo-verification-create/SKILL.md) 仅补齐本次需要的资产，完成后回到本 Skill。若已有资产与当前入口、命令、路由、选择器、操作步骤、副作用或预期行为明显不符，说明地图已漂移：旧地图不能继续作为 PASS 依据，转 [nimo-verification-maintain](../nimo-verification-maintain/SKILL.md) 做定向维护，修复后再回到本 Skill。旧路径恰好还能跑，不等于新行为已被验证。
3. **选择最小相关检查。** 在全部验收场景之外，补上必要不变量与合理影响范围。按变更类型选择真实检查：CLI 变更运行真实命令；API／服务变更调用真实公开接口；UI 变更在运行中的应用里走改动流程；解析器或迁移重放保存输入；性能变更比较前后 profile；存储变更从独立只读视图读回写入值。静态检查、编译和单元测试可作为前置或辅助证据，但不能替代要求真实操作面的场景。该范围存在非显然取舍时，由调用方按 [nimo-show-me-your-work](../nimo-show-me-your-work/SKILL.md) 记录 verification Decision；不要把检查范围选择藏在最终一句“测试通过”里。
4. **确认实例健康与所有权。** 记录本次实例、端口、数据、鉴权和资源所有权。任何时候目标状态可疑，先按项目验证 Skill 的体检方法确认进程、版本、端口和鉴权，再决定是否驱动。工具或运行条件缺失不伪造；记录所缺前提，对应场景保持未验证／不可判定。
5. **走真实用户路径并观察副作用。** 不走内部 setter 或测试专用端点；优先稳定句柄（ARIA 标签、data 属性、提示字符串、路由路径、公开 API 契约）而非坐标。捕获用户动作和结果状态，不只最终画面；写入文件、数据库变更、消息发送等副作用与可见结果一同验证。mock 只用在产品边界已经明确隔离外部系统的地方。
6. **预期先于结果。** 在读取实际结果前固定每个场景的预期，再逐项比对；只打印输出不算通过。保存版本、环境、Shell、完整参数、操作、输出和时间。CLI 证据包含命令、stdout、stderr、退出码；API 证据包含关键请求与响应；状态变更包含只读第二视图；UI 证据包含足以证明动作与结果的截图、trace 或等价记录。
7. **形成逐场景结果与证据。** 每个验收场景、关键不变量和影响范围检查分别记录 `PASS | FAIL | NOT_RUN | NOT_APPLICABLE`、证据位置和原因。必要检查未执行不能改成 PASS。需要 Task Audit 时，每条检查同时形成 `audit.mjs append` 的 `verification` 记录：`check` 使用稳定检查 ID，`source` 使用 Acceptance ID 或明确不变量／影响范围来源，`required` 在首次记录后不得通过重试偷偷降级，`verification` 写真实操作面／验证资产，`evidence` 写证据或未执行原因，`result` 写本步骤真实结果。同一检查重试继续追加同一 Check ID，保留失败到修复通过的历史。
8. **形成总体结论。** 只有当前任务所有必要验收场景均有有效 PASS，且关键不变量／影响范围没有未处理失败时，才能形成 VERIFIED；必要前提不可用则按任务状态形成 BLOCKED，明确跳过或条件不足则保持 UNVERIFIED。把总体 Verdict 和精确 Artifact Version 交给调用方更新 Task Audit Outcome；本 Skill 不自行把 Audit 的结构完整性等同于业务验证通过。
9. **清理且保留证据。** 只清理本次创建的实例和临时状态；绝不按进程名杀。证据保存在清理范围之外，清理后确认仍可读取。清理动作不能改变已经观察到的验证结果。
10. **独立验证。** 独立验证由未参与实现的上下文执行，主 Agent 再读取当前差异、验收映射和证据验收。无法获得独立上下文时按宿主合同降级并明确报告；没有证据的自信结论是危险信号。独立验证要求与 Task Audit 的独立审计要求不同：本 Skill 仍按当前任务验证纪律决定是否需要独立执行，Audit 只记录真实发生的独立性事实。

## 交付格式

交付至少给出一张可审计的场景覆盖表，不需要报告全项目覆盖率：

| 场景／检查 | 来源 | 验证资产 | 结果 | 证据／原因 |
|---|---|---|---|---|
| AC-01 | Task Contract／用户要求 | `.nimo/verification/...` | PASS／FAIL／NOT_RUN | 证据位置或缺口 |

随后给出当前产物版本、总体结论 `VERIFIED | UNVERIFIED | BLOCKED`、失败项、未执行项和合理影响范围。需要 Task Audit 时同时给出已记录的 Check ID 与 Audit 位置。不能用“测试都过了”替代逐场景可追溯关系。

## 边界与交付

- 本 Skill 不修改 Verification Map、harness 或辅助脚本；缺资产转 `nimo-verification-create`，资产漂移转 `nimo-verification-maintain`，再回到本 Skill执行。
- 本 Skill 不把 `audit validate` 作为业务测试；Audit 校验只检查记录关系是否自洽。
- 不因项目整体 Verification Coverage 不完整而自动阻塞当前任务；只对当前任务必要场景、关键不变量和合理影响范围负责。
- 遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。
- 交付具体产物、当前版本证据、未完成项及原因。跳过保留理由，不能用 Skill 名称列表代替成果。
