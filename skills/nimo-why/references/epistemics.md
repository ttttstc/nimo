# 认识论

当证据是历史的、残缺的、有时互相矛盾时，如何推理置信度，以及如何在不把它压扁成虚假确定性的前提下传达它。

代码不携带自身的动机。你能读到代码做什么；读不到它*为什么存在*。那活在提交、PR、工单、文档和对话里——全都不完整、有偏、有时干脆缺失。假装相反，只会产出听起来自信的猜测，误导用户。

## 置信度层级

最终输出里的每个论断必须落在其中一层。层级决定论断进入哪个输出小节、如何措辞。

### 1. 直接（Direct）

一条显式的、文本的引用，直接回答问题。不是"代码做了 X，所以作者一定想要 X"，而是作者真的*写下来*的、说明为什么的东西。

例子：
- 一段写着"这修复了拥有超过 1000 个条目的用户无法分页的 bug"的 PR 描述
- 一张写着"我们加这个是因为客户 Acme 在他们的安全评审里提出"的工单
- 一条写着 "// clamp 到 100，因为上游 API 拒绝更大的值" 的代码注释
- 一篇写着"我们选方案 A 不选方案 B，因为需要跨重启的持久化"的设计文档
- 一条作者写的"换成这个方案，旧的在测试里不稳定"的聊天消息

措辞：自信、现在时。"这存在是因为 X。"引用来源。

### 2. 支撑（Supported）

多条间接证据汇聚。没有单一来源显式陈述它，但跨来源的模式使之很可能。

例子：
- PR 标题说"提升性能"，工单带 "perf" 标签，周围提交全都改同一条热路径
- 随变更一起加了多个测试，全都用超大输入压边界情况
- 作者同一周的其他 PR 描述里都提到同一次事故

措辞：自信但明确是推导出的。"证据强烈指向 X：[具体条目]。"引用多个来源。

### 3. 推断（Inferred）

对上下文的一个合理读法，但没有任何东西显式支撑它。读者应当理解这是*你的解读*，不是记录里的事实。

例子：
- PR 没说为什么，但错误当时正在生产发生（从事故频道的时间线推断）、修复很仓促（当天合并），所以很可能是热修复。
- 函数名暗示重试逻辑；重试次数是 3；这与代码库其他地方可见的团队"重试 3 次"惯例吻合。

措辞：限定。"看起来""很可能""表明""与……一致""一种解读是"。把推断链写显式："给定 A 和 B，C 看起来很可能，因为 D。"

### 4. 猜测（Speculative）

一个貌似合理的假设，但证据单薄、其他解释同样吻合。呈现这些有价值，但要清晰标注为猜测。

例子：
- "这可能是一个浏览器 bug 的变通方案，而那个 bug 后来修掉了，但我们没找到当时的证据。"
- "这个阈值有可能是为了匹配某个 SLA 承诺，但没有 SLA 文档引用它。"

措辞：显式标注猜测。"一种可能是 X，但我们没有直接证据。"通常放在"竞争假设"小节，与其他可能性并列。

### 5. 未知（Unknown）

你找过、没能找出。一个有效且重要的结果。记录它。

措辞："我们搜了 X、Y、Z，没找到关于原因的证据。"具体说明*搜了什么*。"我们查不出来"不如"我们用工单系统搜了关键词 A 和 B，扫了 2023 年以来触及这个文件的 6 个 PR，在仓库里 grep 了匹配该阈值的字符串字面量；都没浮出理由"有用。

## 措辞指南

### 承载置信度的词。谨慎使用。

这些词暗示**直接**或**支撑**级置信。不要用于推断。

- "因为"（because）。暗示有证据的因果论断
- "原因是"（the reason is）。同上
- "被设计来"（was designed to）。宣称作者意图
- "修复了""解决了""搞定了"。宣称变更达成了目标
- "团队决定了"。宣称发生过一次群体决策

使用这些词时，旁边应当立刻有引用。

### 限定词。用于推断。

- "看起来"（appears to）
- "似乎"（seems to）
- "很可能"（likely）
- "表明"（suggests）
- "与……一致"（is consistent with）
- "一种解读是"（one reading is）
- "貌似有道理地"（plausibly）
- "可能是"（may have been）
- "证据指向"（the evidence points toward）

这些词表明你在解读，不是在转述。在"我们可以合理推断什么"小节大量使用。

### 要避免的词

- "显然"（obviously）。真显然的话，用户就不会来问
- "很明显"（clearly）。几乎总是引出一个并不明显的论断
- "当然"（of course）。同上
- "只是"（just，如"它就是个性能优化"）。轻慢，且通常掩盖不确定性
- "我觉得""我认为"。你在综合证据，不是发表个人观点。用"证据表明"（the evidence suggests）。

### 避免合理化

今天"说得通"的代码，可能是为已不再适用的原因写的，或者写的时候就是错的。不要给混乱的历史事后补一个干净的动机。

抵制这些冲动：
- 假设作者做的是"对"的事，再倒推理由
- 假设代码库里的模式一致性是有意为之，而它可能只是复制粘贴
- 把证据缺失当成缺失的证据（"没人提过安全顾虑，所以当时肯定不是顾虑"）

## 谄媚陷阱

用户的 why 问题经常内嵌假设："我们为什么这么干？我猜是为了性能。"不要简单确认它。把它当作候选之一，独立检验证据。证据支持就带引用地说；不支持就说不支持，并呈现证据*确实*支持的东西。

用户的猜测是调查的提示，不是待验证的结论。

## 证据矛盾时

两个来源不一致（PR 描述说一套，工单说另一套）时，两个都摆出来。不要挑符合更整齐叙事的那个。典型模式：

- **工单说**"客户 X 的合规要求需要这个"
- **PR 说**"清理这个领域的技术债"

两个都可能是真的（工单驱动了这项工作，PR 是作者对它的表述），也可能一个是错的。带着各自的引用呈现两者，让用户裁决。

## 证据缺失时

一句诚实的"我们不知道"是本 Skill 能产出的最有价值的输出之一。用户由此知道：

- 答案不在显眼的地方
- 需要问人（原作者、产品负责人、团队负责人）才能知道
- 或者可以决定这个问题不值得继续追

不标记缺口、而用一个自信的猜测填上，会主动伤害用户；他们会按猜测行动。

碰到缺口时，具体点名：
- 你想回答什么问题
- 你搜了哪些来源
- 每个来源里搜了什么
- 找到了什么（什么都没有，或只有擦边的材料）

## 定稿前的校准检查

交付前，汇总者应过一遍"我们发现了什么"和"我们可以合理推断什么"里的每个论断，问：

1. 这个论断有引用吗？没有就补一个，或者挪到"推断"/"假设"。
2. 措辞与层级匹配吗？（直接级可以用"因为"；推断级不能。）
3. 我有没有把代码本身当作它自己意图的证据？有就不是证据。删除或重新分类。
4. 输出里有"我们不知道什么"小节吗？没提到任何缺口是可疑的。要么证据罕见地完整，要么有东西被扫到了地毯下。
