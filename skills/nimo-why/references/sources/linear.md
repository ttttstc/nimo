# Linear 工单

## 这个来源包含什么

- 描述功能、bug 及其动机的 issue
- 挂在 issue 上的项目文档（常是 PRD 或规格）
- 父/子工单关系（更大的立项 → 具体工单）
- 工单评论（澄清、范围变更、"我们为什么做这个"的理由）
- 标签（如 `compliance`、`customer-request`、`perf`）标示动机的类型
- 解释范围变更的状态更新
- 附件与关联的 GitHub PR

Linear 是产品/业务上下文常在的地方："客户 X 提了所以我们做这个""这是 Q3 合规立项的一部分"这一层。

## 怎么搜

使用 Linear 连接器（工具名以 Linear MCP 为例）。

1. **先看关联工单。** 种子提交或 PR 引用了工单 ID（如 `ENG-1234`、`[BUG-567]`）时，先用 `get_issue` 拉取它们。完整读工单，包括评论。
2. **按关键词列相关工单。** 用 `list_issues` 做文本搜索，搜功能名、关键符号或业务术语。多试几种措辞。
3. **走工单树。** 落到一张子工单上时，拉取它的父级。子工单是战术的；父级常带着"为什么"。
4. **读项目文档。** 工单属于某个项目时，用 `get_project` 并检查挂载的文档。项目级文档是规格与理由最常被捕获的地方。
5. **查标签与里程碑。** 标签暗示动机的类别（客户请求、事故跟进、合规）。里程碑把工作绑到截止日期，而截止日期经常暴露动机。

## 这里的好证据长什么样

- 一条陈述业务问题的工单描述："客户 Acme 因为他们的 SOC2 审计需要 X"
- 一条记录决策的评论："我们定了方案 B，因为方案 A 要动计费服务"
- 一张标题像立项的父工单："Q3 企业就绪"或"降低支付失败率"
- 一份挂载的 PRD 或规格
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 这类标签

## 常见坑

- **范围漂移。** PR 引用的那张工单可能已被关闭、又以不同的范围重开。读完整历史。
- **机械的模板。** 有些团队要求填 "Why" 小节但填的是模板话。泛泛的文本（"改善用户体验"）多半不是真答案。
- **过期工单。** 老工单反映的常是后来变了的一版计划。查日期，与代码的上线日期交叉核对。
- **按重复关闭的链。** 沿 duplicate-of 关系一路追回到正主工单。
- **私有工作区内容。** 无权访问的工单记为缺口，不要猜测。

## 返回什么

每张相关工单：
- 工单 ID 与标题
- 从描述或评论引用的问题/动机（不要转述；汇总者需要确切文本来引用）
- 标签、父工单、项目
- 作者、创建日期、关闭日期
- 工单链接（如有）
