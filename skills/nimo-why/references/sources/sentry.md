# Sentry 错误历史

## 这个来源包含什么

Sentry 是"出过什么事"的档案。对防御性、纠正性或错误处理代码，它经常持有直接动机：那些推动某人加上一个检查、catch、重试或兜底的具体异常、堆栈与频次。

- **issue。** 按指纹分组的错误，带计数、first/last-seen 时间戳、受影响发布与评论
- **事件。** 一个 issue 里的单个错误实例（堆栈、标签、用户上下文）
- **发布。** 部署记录与关联 issue（对"哪个版本修好了这个？"有用）
- **replay。** 用户可见错误的会话录制（若启用）
- **profile。** 性能剖析数据（对"为什么"用处小；对"多慢"有用）
- **issue 评论与指派。** 有时含工程师对根因的备注

Sentry 提供的最有价值的东西是**时间相关性**："issue X 创建于 2024-01-02，峰值 500 事件/天，在 2024-01-15 的 v2.14.0 之后不再出现——那个发布了防御检查的版本。"

## 怎么搜

使用 Sentry 连接器（工具名以 Sentry MCP 为例）。

1. **定向。** 不知道 project slug 与 organization 时：

   ```
   find_organizations
   find_projects
   ```

2. **搜索与目标相关的 issue。**

   ```
   search_issues (自然语言，如 "errors in PaymentService timeout"、"unhandled exceptions in uploadFile")
   ```

   好的查询成分：目标处理的异常类名、目标的函数或类名、目标检查的错误消息串、目标的文件路径。

3. **按发布与时间窗口收窄。**

   ```
   search_issue_events (按发布、时间、环境、trace ID、标签过滤)
   get_issue_tag_values (看某 issue 在版本、用户、环境上的分布)
   ```

   对一个可疑 issue，检查：
   - **First seen。** 错误何时开始出现？
   - **Last seen。** 何时停止？与目标的上线日期对得上吗？
   - **受影响发布。** 哪些版本见过它？哪一个是修复版？
   - **频次轨迹。** 尖峰过，然后被解决了吗？

4. **拉取完整事件看上下文。**

   ```
   get_sentry_resource (传一个 Sentry URL 或 type+ID)
   ```

   堆栈穿过目标代码吗？标签与操作轨迹与目标防御的条件吻合吗？

5. **检查目标附近落地的发布。**

   ```
   find_releases (目标提交日期前后)
   ```

   把发布版本与 PR 的合并日期交叉核对。

6. **少用 Seer。**

   ```
   analyze_issue_with_seer
   ```

   Seer 产出 AI 根因分析。可以当假设生成器用，但要当作推断，不是权威。实际的事件与堆栈才是一手证据；Seer 的叙事是二手的。

## 这里的好证据长什么样

- 一个 issue 的 **first seen** 在目标的 PR 前不久、**last seen** 在其后不久，暗示目标处理了这个错误
- 穿过或落在目标函数上的堆栈，展示被防御的确切失败模式
- PR 作者在 issue 上描述修复的评论
- 目标的 PR 描述或提交信息引用某个 Sentry issue 的 URL 或 ID
- 一个高事件量的 issue 在包含目标的发布之后停止

## 常见坑

- **分组漂移。** Sentry 按指纹分组错误。重构或重命名会让"同一个"错误换一个 issue ID 继续存在。某 issue 突然终止时，可能只是被重新分组了。查紧随其后的新 issue。
- **发布相关是嘈杂的。** 一个发布含很多提交。issue 在 v2.14.0 停止不能证明是目标修的；同发布的其他变更也可能修了它。与目标的确切提交交叉核对。
- **静默修复。** 有时错误停止是因为上游变了，不是因为防御代码。相关性暗示修复；不证明作者身份。
- **resolved 不等于 fixed。** issue 可以在没有任何代码变更的情况下被手动标记 "resolved"。把 `resolved` 当人工标记，不当作代码修好了它的证据。
- **Seer 幻觉。** Seer 能生成貌似自信但不对的解释。下论断时退回实际的事件、堆栈与时间戳。
- **采样。** 有些项目激进地采样事件。低事件量可能只是高采样，不是罕见错误。拿不准就记缺口。

## 返回什么

每个相关 issue：
- issue ID 与标题
- project 与 organization
- first seen / last seen 时间戳
- 事件数（及采样率，若知道）
- 受影响发布
- 展示与目标相关性的代表性堆栈片段（逐字摘录，不是摘要）
- first/last-seen 与目标上线日期的相关性
- issue 链接
- 任何作者评论或解决备注
