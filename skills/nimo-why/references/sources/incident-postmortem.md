# 事故与复盘上下文

不是一个独立的来源，而是一个**跨领域的视角**。事故经常是防御性代码的动因（"X 故障之后我们加了这个检查"），所以当目标看起来是防御性的（空值检查、重试逻辑、超时处理、限流、特性开关）时，在每一个可用的来源里专门追查事故史：

- **长文档（如 Notion）**：搜索提到目标文件、功能或错误串的复盘
- **工单跟踪（如 Linear）**：找带 `incident`、`sev-*`、`postmortem-action-item`、`reliability` 标签的工单
- **团队即时沟通（如 Slack）**：在目标代码加入的日期前后搜索 `#sev-*` 和 `#incident-*` 频道
- **Git**：消息形如 "fix for incident"、"add defensive check"、以及 "revert" 后跟 "re-apply with..." 的提交是强信号
- **基础设施可观测性（如 Datadog）**：`search_datadog_incidents` 查带时间线的正式事故记录；作为复盘整改项创建的仪表盘和监控器
- **错误 / 异常追踪（如 Sentry）**：first-seen/last-seen 窗口与目标 PR 上线日期对齐的 issue；穿过目标代码的堆栈
- **产品分析数仓（如 Databricks）**：分类错误条件的产品分析事件（客户端上报的失败、用户可见的重试事件等）经常在事故窗口尖峰。目标 PR 上线后该事件计数下降，是目标代码解决了用户可见症状的旁证——即使 Datadog/Sentry 信号嘈杂。

找到事故链接，就抓取完整的复盘。复盘通常有一个直接对应代码变更的"整改项（Action Items）"小节。当多个来源相互印证时（一个 Datadog 事故 ID 出现在 Linear 工单里，工单出现在 Notion 复盘里，复盘出现在链接到目标 PR 的 Slack 讨论串里，且 Databricks 的错误事件计数在修复后下降），证据尤其强。

当代码的防御性特征使"事故驱动的起源"可信时，值得在上面花时间。对看起来不防御的代码，跳过这一视角。
