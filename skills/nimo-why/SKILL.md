# 调查设计动机（why）

调查代码背后的动机与意图。它为什么被写成这样？当时考虑过哪些边界情况？哪些产品、业务或运维约束塑造了这个设计？拒绝了哪些备选方案，为什么？

`nimo-how` 的姊妹 Skill。`nimo-how` 回答代码做什么、怎么工作；`nimo-why` 回答是什么力量造就了它的形状。

## 本 Skill 如何工作

历史上下文散落在七类证据里：源码历史、工单/issue 跟踪、长文档、团队即时沟通、基础设施可观测性、错误/异常追踪、产品分析数仓。你无法从问题本身预判答案在哪一类，所以本 Skill 在运行时枚举当前宿主提供的连接器（MCP 或等价接口），把每个连接器映射到一个类别，并行查询全部七类，再以显式的置信度校准做汇总。已搜索类别返回的空结果（null result）本身是关于"这个决策如何做出"的一等证据；与正向发现一起报告。默认姿态是覆盖，不是最小化。

## 工作姿态

以一个谨慎、小心、精确的调查者姿态运作。像侦探从残缺的档案里拼一桩历史旧案。档案单薄时，直说。

具体要求：

- **证据先于叙事。** 先收集碎片，再看它们支撑什么故事。绝不先挑一个故事再去找符合它的证据。
- **精确优先于润色。** 宁要精确的引文和引用，不要顺滑的转述。任何论断都应能被读者追溯到来源并在一分钟内验证。
- **考虑你没看到的。** 找到的证据是抽样，不是全部真相。下结论前问自己：如果另一种解释成立，我应当能看到什么？我找过吗？
- **点名缺口。** 线索断了、来源不可搜索、问题没有答案——如实记录缺口。不要用一个听起来权威的猜测糊弄过去。
- **刻意使用限定语。** 证据是间接的，语言就要体现出来（"看起来""很可能""表明"）。与置信度匹配的措辞是产出的一部分，不是汇总者可以覆盖的风格选择。
- **不靠读代码走捷径。** 代码告诉你它做什么，很少告诉你它为什么存在。抵制从当前代码形状反推动机。

这套姿态是工作方法，不是免责声明。

## 核心认识论

本 Skill 从残缺的历史证据中拼出**补丁式理解**。工单会过期。聊天串会被删除。提交信息会说谎。人在 PR 描述和实现之间改主意。原作者可能已经离职。

对你知道的和你在推断的东西保持毫不留情的诚实。目标不是一个令人满意的故事，而是呈现证据、校准置信度、让用户自己判断。

原则：

- **引用一切。** 每个关于意图的论断都应指向具体的提交哈希、PR 编号、工单 ID、文档 URL、聊天永久链接或代码注释。给不出引用，它就是推断，不是事实，必须如此标注。
- **优先"看起来"而非"因为"。** 证据间接时使用限定语。把确定的措辞留给直接的、显式的证据。
- **呈现矛盾。** 两个来源不一致时，两个都摆出来。不要悄悄挑一个符合你叙事的。
- **承认缺口。** 你搜过的来源都没有答案，就直说。一句诚实的"我们没能找出原因"胜过一个自信的猜测。
- **多个假设并存是合法的。** 证据同时符合几个故事时，把它们连同各自的证据一起呈现，让用户三角定位。
- **警惕合理化。** 今天看起来合理的代码，可能是为已不再适用的原因写的，甚至当初就没有好理由。不要事后补一个干净的动机。

阅读 `references/epistemics.md` 获取完整的置信度框架与措辞指南。汇总者必须遵循它。

## 第 1 步：理解目标与问题

解析用户在问什么。**目标**通常是一段代码、一个模式、一个功能或一个具名的设计决策。**问题**通常是：

- "X 为什么被设计成这样？"设计动机。
- "我们为什么做 X 而不是 Y？"权衡或备选方案。
- "哪些边界情况促成了这个？"防御性推理。
- "什么业务或产品约束导致了这个？"外部强制函数。
- "这段代码为什么还存在？"死代码领域。
- "X 的历史是什么？"大范围考古。

目标模糊时（"我们为什么这么干？"且没有明确指代），从会话上下文（打开的文件、最近的修改、光标位置、刚讨论过的内容）做最合理的猜测。简要说明你的解读，让用户能纠正你，然后继续。

## 第 2 步：建立代码锚点

在派出调查者之前，把调查锚定在具体代码上。你需要：

- 相关的文件路径与行范围
- 关键符号（函数名、类名、常量）
- 一份初始提交列表：触及目标的最近几条提交
- 合并提交里的 PR 编号（subject 行的 `(#1234)` 模式）

在主上下文里就地完成这一步。它很便宜，而每个调查者都需要它。

```bash
# 查看目标各行最后一次被谁、何时改动
git blame -L <start>,<end> <file>

# 文件完整历史，含补丁，穿透重命名
git log --follow -p -- <file>

# 触及该文件的最近 N 条提交，PR 编号可见
git log --oneline -20 -- <file>

# 从提交信息提取 PR 编号
git log -1 --format=%B <commit>
```

对任何实质性提交，用 `gh` 拉 PR 正文与讨论：

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

把这些捕获为种子上下文（文件路径、符号、提交、PR 编号、关联的工单 ID），传给调查者，免得他们重新发现一遍。

## 第 3 步：派出并行调查者（默认姿态）

**默认执行完整的并行调查。** 每类证据活在不同种类的系统里，不亲自看一遍，你无法从问题本身判断答案在哪一类。所以默认对所有可用类别并行展开调查。

### 发现（枚举可用连接器）

派出调查者之前，先枚举当前宿主在运行时提供的连接器/工具（MCP 或等价接口）：查看宿主暴露的可用工具清单；清单不可见时，通过宿主的连接器配置（MCP 服务器配置或等价机制）确认哪些可用。宿主没有某一类连接器时，把该类别记为缺口（"该类别在本环境不可搜索"）——不跳过、不虚构。

把每个可用连接器映射到一个证据类别：

1. 源码历史
2. 工单 / issue 跟踪
3. 长文档
4. 团队即时沟通
5. 基础设施可观测性
6. 错误 / 异常追踪
7. 产品分析数仓

源码历史通过 git 和 `gh` 始终可用。其余六类按连接器名称、服务端说明、工具名称与资源描述来分类。一个连接器可能适配多个类别时，选择与其主要证据匹配的那个；把有歧义的情况记入覆盖图。

目标是完整的**覆盖图**，不是最小覆盖。工单系统返回空结果是"该决策没有立项"的证据，这本身是有用的事实。把空结果记录下来，不要跳过搜索。

尽量在同一批里启动全部匹配的调查者使其并发执行。每个类别一个调查者，让每个调查者专精一个工具的查询词汇与结果形态。不要让一个 Agent 覆盖多个连接器。

派发要求（每个调查者）：

- 用宿主提供的独立子 Agent / 独立上下文能力派发；宿主没有独立上下文能力时，诚实降级：主 Agent 按类别逐一顺序执行调查，并在最终输出的"查询来源"部分明确记录该降级。
- 模型：用户配置的 why-investigators 模型。
- 调查者必须保留对连接器/工具的访问能力：**不要在剥离工具访问的受限模式下运行**，那会整体禁用依赖连接器的调查者。源码历史调查者理论上不受影响，但保持全体模式一致。调查者仍然不应写入任何东西——这是纪律姿态，不是沙箱。
- 授权边界：只读取用户授权的数据源；不扫描其他项目的私人会话或无关空间；遵守宿主的权限模式。

每个调查者拿到：

1. `references/investigator-prompt.md` 的基础提示词
2. 所选连接器对应的类别手册 `references/sources/<source>.md`，按 `references/source-playbook.md` 的索引选取，并按实际可用的连接器改编
3. 若目标代码看起来是防御性的（空值检查、重试逻辑、超时处理、限流、特性开关、出口防护、OOM 处理器），附加跨领域的 `references/sources/incident-postmortem.md`
4. 第 2 步的代码锚点（文件路径、符号、提交哈希、PR 编号、工单 ID）
5. 用户的原始问题

### 调查者名册。每个可用证据类别一个

为每个有匹配连接器的类别派出一个调查者。每个调查者恰好负责一个工具/连接器。

每个条目列出该类别物理上包含什么、以及它独有地呈现哪一种"为什么"。用它来知道该期待什么、当某类别返回空时如何命名缺口、以及（仅在罕见的可证明无关的情况下）为跳过辩护。各类别之间有重叠，但每个都独占一类其他类别无法恢复的证据。

1. **源码历史调查者**。git 历史、`gh` 的 PR、代码注释、测试。始终派出；唯一保证可用的来源。最擅长呈现*评审期间留下的实现时动机*。陈述问题的 PR 描述、辩论备选方案的评审线、编码非显然约束的内联注释、编码动机性边界情况的测试名、链接工单或事故的提交信息。因为直接绑定实际发布的 diff，最可信。

2. **工单 / issue 跟踪调查者**（如 Linear、Jira、GitHub Issues、Plane、Shortcut 的连接器）。工单、项目文档、状态更新、规格附件。最擅长呈现*产品或业务的强制函数*。客户请求（"Acme 为他们的 SOC2 审计需要 X"）、合规截止日期、上级立项框架（"Q3 企业就绪"）、工单级的范围变更、给动机分类的标签（`customer:*`、`incident-followup`、`compliance`、`perf-regression`）。当 why 在工程之外时最强。

3. **长文档调查者**（如 Notion、Confluence、Google Docs、Coda 的连接器）。PRD、规格、RFC、设计文档、ADR、复盘、团队页面、会议纪要。最擅长呈现*长篇设计动机*。问题陈述、显式的"考虑过的备选方案"与"被拒绝的方案"小节、设定优先级的战略文档、定稿决策的 ADR、与代码直接挂钩的复盘整改项。why 在变成代码之前被写下来的地方。

4. **团队即时沟通调查者**（如 Slack、Discord、Microsoft Teams、Mattermost 的连接器）。功能名与符号搜索、PR URL 提及、事故频道（`#sev-*`、`#incident-*`）、上线日期前后作者账号的动态。最擅长呈现*从未进入文档的实时审议*。事故期间的紧急决策、PR 作者与评审者之间的问答、随口的"我们定了 X 因为 Y"讨论串、不值得写 PRD 的小改动动机。当源码、工单、文档的纸面痕迹单薄时尤其重要。

5. **基础设施可观测性调查者**（如 Datadog、New Relic、Honeycomb、Grafana、Splunk 的连接器）。指标、监控器、仪表盘、日志、APM trace、正式事故记录。基础设施/运行时视角。最擅长呈现*促成代码的基础设施与运行时现实*。数字与代码常量吻合的监控阈值、PR 合并前窗口的指标尖峰、作为复盘整改项创建的仪表盘、引用目标的事故时间线。当目标对基础设施信号（超时、重试、限流、熔断器）做出反应时最强。

6. **错误 / 异常追踪调查者**（如 Sentry、Rollbar、Bugsnag、Airbrake 的连接器）。issue、事件、堆栈、发布记录。最擅长呈现*促成防御性或纠正性代码的具体异常与错误轨迹*。穿过目标函数的堆栈、first-seen/last-seen 窗口恰好夹住 PR 上线日期的 issue、显示错误在特定版本停止的发布关联。对 catch 块、空值防护、类型检查、重试等防御最强。

7. **产品分析数仓调查者**（如 Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift 的连接器）。产品分析事件、实验与特性开关曝光表、用量与计费事件、查询历史、数仓遥测。产品/数据视角。通过覆盖*上线日期前后的用户行为与数据现实*（而非基础设施指标）与基础设施可观测性互补。最擅长呈现*塑造代码的产品与数据现实*。功能使用轨迹（上线一两天内从零到稳定量的阶跃，是该 PR 发布了此功能的有力旁证）、与上线决策挂钩的实验/开关曝光数据、揭示阈值常数来源的上线前分布（如 `limit = 128 * 1024` 恰好匹配某个上传大小列的 p99）、迁移/回填的数据管道规模证据。对开关门控代码、实验驱动上线、数据迁移、"这个数字从哪来"的问题最强。

### 何时跳过某个调查者

只有给出**显式的、书面记录的理由**才能跳过，理由写进最终输出的"查询来源"部分。两种有效理由：

- **该类别在本环境没有可用连接器。** 标记为缺口，而不是选择。例："团队即时沟通跳过。无匹配连接器，对话记录不可搜索。"
- **来源可证明地无关**，而不只是"大概无关"。很高的门槛。例："错误追踪跳过。目标是构建期脚本，没有运行时代码路径。"而不是"大概不在错误追踪里，这是个功能不是错误"。

"这是纯功能代码，错误追踪里不会有东西"**不**充分，"我怀疑长文档里不会有这个"也不充分。执行搜索，让空结果自己说话。一个调查者返回空的代价是一个子 Agent；漏掉一份实际存在的设计文档的代价是一个错误答案。

若你的范围评估表明目标是单提交的琐碎目标、PR 描述已含完整答案，可以在**确认全部七类可用搜索都冗余之后**才内联作答，并显式说明这一点。这应当罕见。

## 第 4 步：汇总

派发一个汇总者子 Agent（同样使用宿主的独立子 Agent / 独立上下文能力；不可用时诚实降级为主 Agent 执行，并记录降级）：

- 模型：用户配置的 why-synthesizer 模型。
- 汇总者不得在剥离工具访问的受限模式下运行：它的质量检查会抽查引用，可能需要连接器访问；受限模式会让这一检查失效。

汇总者拿到：

1. 调查者的发现，包括所有空结果与任何带理由跳过的类别
2. 第 2 步的代码锚点（文件路径、符号、提交哈希、PR 编号、工单 ID）
3. 用户的原始问题
4. `references/epistemics.md` 的认识论框架
5. `references/synthesizer-prompt.md` 的汇总者提示词模板

它的职责是最终输出：一份按置信度加权、带证据引用的叙述，明确分离"我们知道什么"与"我们在推断什么"，并诚实承认缺口与返回空的来源。

## 第 5 步：呈现

把汇总者的输出呈现给用户。可以为清晰起见轻度编辑，或补充会话中的上下文，但**不要改写置信度语言**。认识论框架就是产品本身。为了让答案听起来更权威而抹掉限定语，正是这个 Skill 要防止的失败模式。

## 输出格式

最终输出使用以下结构。可按需调整，但置信度分离必须保持。

**问题**。简洁重述用户问了什么。

**目标代码**。文件路径、行范围、关键符号。一两行让读者锚定。

**我们发现了什么（直接证据）**。带显式引用的论断（PR 编号、工单 ID、文档 URL、聊天永久链接、提交哈希、file:line 的代码注释）。每条都是有文本证据的事。用现在时，引用或转述来源。

**我们可以合理推断什么**。有间接证据或信号组合良好支撑、但没有任何地方显式陈述的论断。每条必须解释推断链："给定 A 和 B，很可能 C。"使用限定语言（"看起来""很可能""表明"）。

**竞争假设**。证据符合多个故事时列出来。每个假设给出：假设本身、支持证据、反对或缺失的证据。记录不支持分出胜负时，不要强行选一个赢家。（有明确答案时跳过本节。）

**我们不知道什么**。显式缺口。用户问过但证据没回答的问题。搜过但一无所获的来源。要具体。"我们在工单系统搜了 'rate limit'，没有找到讨论这个具体阈值的工单"比"我们不知道为什么"有用。

**查询来源（Sources Consulted）**。每个调查者一行，包括一无所获的。读者应能一眼看到 (a) 查询了哪些来源，(b) 哪些返回空，(c) 哪些被跳过及原因。这张覆盖图让用户能判断广度，并在明显遗漏时重定向。

每行格式：`- <来源>: <搜了什么>. <发现了什么，或"无相关结果"，或"跳过。原因">.`

示例：
- 源码历史（git/gh）：`git log --follow backend/retry.ts`，PR #49074、#47812。发现 PR #49074 引入指数退避并关联 ENG-4421。
- 工单跟踪（Linear）：搜索 "retry" 和 ENG-4421。发现 ENG-4421 父工单，但没有关于退避参数的讨论。
- 长文档（Notion）：搜索 "retry policy"、"backend retries"、"ENG-4421"。无相关结果。
- 团队即时沟通（Slack）：跳过。本环境无匹配连接器。缺口：对话记录未搜索。
- 基础设施可观测性（Datadog）：搜索 `retry_count` 指标与 2024-08-14 前后的监控器。发现监控器 "Upstream 5xx rate > 1%" 与 PR #49074 同日创建。

## 必须避免的常见失败模式

- **自信的讲故事。** 用单薄证据搭出的貌似合理的叙事。没有引用的条目进"推断"或"假设"，不进"我们发现了什么"。
- **把代码当作它自己意图的证据。** "处理了空值情况，因为它检查了空值"是机制，不是动机。动机来自外部来源（PR 讨论、工单、注释、对话），否则必须标注为推断。
- **近因偏差。** 假设最近的提交是权威的。当前形状常常是许多更早决策的堆积。往回追。
- **谄媚式附和。** 用户提出一个原因（"我猜这是为了性能？"）时，把它当作一个假设并独立检验证据，不要直接确认。
- **跳过缺口小节。** 对查不到的东西的诚实清点是价值的一部分。
- **凭预期跳过调查者。** 事先断定"长文档里大概没有"或"这不是错误追踪的事"而不搜索。默认全七类的姿态就是为了防止这个。空结果是数据点；被跳过的搜索是盲区。
- **把调查者合并成一个 Agent。** 每个连接器有自己的查询词汇、结果形态和坑；混在一起稀释专精度、让覆盖更难推理。始终一类一个调查者。
