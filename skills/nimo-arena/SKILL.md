# 候选方案竞技场

针对同一任务并行生成 N 个候选。完整阅读每个候选，按统一标准比较，选择最强者作为基线，再把其他候选中真正有价值的部分整合进去。最后验证综合结果。

## 开始

开始前按阶段建立任务清单：

1. 定义任务与评分标准
2. 并行生成候选
3. 交叉评审
4. 选择基线
5. 整合优点
6. 验证结果

## 阶段 A：定义任务与评分标准

所有候选收到同一份任务说明，因此任务说明就是共同契约。

1. 明确每个候选要产出的具体产物。
2. 根据当前任务定义 3～6 条可直接判分的成功标准。评分标准必须具体，供阶段 D 做比较；候选只接收任务本身。
3. 选择执行者。优先使用用户配置的 arena runners；未配置时，在宿主实际可用的模型里选择多个候选。需要判断差异时优先不同模型家族；主要依赖生成多样性时，同一模型运行多次也可以。
4. 为每个候选分配独立输出位置。优先使用独立 worktree；无法使用时放在彼此隔离的临时目录。多个候选不得同时写同一工作区，遵守 nimo-principle-separate-before-serializing-shared-state。

## 阶段 B：并行生成候选

宿主支持并行或后台子 Agent 时，一次性派发全部候选。每个候选拿到：任务、共享事实基础的位置、自己的输出位置，以及“同时交付产物和简短设计理由”的要求。

宿主不支持并行时，按委派纪律顺序执行并保持候选互相不可见，明确记录降级。

每个候选的理由必须说明考虑过哪些备选方案、拒绝了什么以及为什么。有候选没有产出时，以剩余候选继续，并在综合记录中注明。

## 阶段 C：交叉评审

全部候选完成后，再启动一个只读交叉评审者。优先使用与父 Agent 不同的模型家族；只有单模型时按委派纪律降级并记录。

交叉评审者看到评分标准和按路径标识的候选，对每条标准逐项评分，并给出推荐的基线及理由。交叉评审可以和父 Agent 自己阅读候选同时进行，但不能在候选仍在写入时启动。

## 阶段 D：选择基线

选择前完整阅读每个候选。逐条评分标准比较，而不是凭整体印象挑“看起来最好”的那个。

把自己的判断与交叉评审结果对照。一致时视为强信号；不一致时，重新检查双方理由和评分标准是否含糊，再决定。

当候选接近时，优先选择边界更清晰、公共接口更小、未来维护者更容易在不破坏不变量的前提下继续扩展的方案，遵守 nimo-principle-laziness-protocol。

在基线产物旁记录一份简短综合说明，写清选择结果、理由和交叉评审结论。

## 阶段 E：整合其他候选的优点

重新检查每个未入选候选，找出值得移植到基线的少量高价值部分。通常每个候选只有一两点值得保留，而不是整套方案一起搬过去。

把这些部分按基线方案的整体设计重新整合，不要机械复制。最终结果必须保持一个一致的心智模型。记录整合了什么、来自哪个候选，以及哪些内容被拒绝、为什么。

如果多个候选独立收敛到同一种整体结构，这是高价值一致性信号，可以直接采用共识结构；如果候选彼此差异巨大，通常说明阶段 A 的问题定义不足，应重新定义任务后再跑，而不是把分歧平均掉。

## 阶段 F：验证

综合后的产物必须像任何正式交付一样验证，遵守 nimo-principle-prove-it-works。

如果验证暴露出之前没有发现的问题，判断是任务定义有误，还是候选中已经出现过但整合时遗漏。前者回到阶段 A，后者回到阶段 E。不要用临时补丁掩盖验证失败。

## 输出

交付：

- 一个综合后的最终产物。
- 一份简短综合记录，包含基线候选、吸收了哪些内容及其来源、拒绝项、退出候选（如有）和验证结果。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。交付具体产物、当前版本证据、未完成项及原因。跳过步骤必须记录理由。
