# 把领域建模进结构

把真实领域编码进数据结构，而不是散落在条件判断里。

## 适用

编写有状态逻辑；代码分支很多；或同一形状假设在多个文件里重复出现。

## 为什么存在

散落的布尔值、重复的形状假设、跨文件分布的分支，都是偶然复杂度。一个与领域匹配的结构能让无效状态无法表示，并直接删掉分支。写代码时顺手选对结构是便宜的；事后补回它读起来像一次重构，于是一直被推迟。

## 结构选型

遇到以下情形，优先选用对应结构：

- 用状态机替代散落的布尔值、阶段标志或生命周期检查。
- 用类型化对象/模型替代松散参数或重复的形状假设。
- 用 map、注册表、查找表或可辨识联合替代散落在各文件的分支。
- 用 reducer 或命令/事件模型替代即兴的状态变更。
- 模块围绕同一领域知识组织，而不是按加载、验证、转换、保存这样的执行序列组织。执行顺序不是所有权。
- 用小的模块边界收拢重复出现的行为、所有权或不变量。
- 数据访问模式需要时，用队列、缓存、索引、图/树或规范化集合。
- 其他合适的结构。以上只覆盖常见情况。都不合适时，先弄清代码绝不允许什么、数据如何被读取，再找恰好编码这些约束的结构。

## 反模式

不要强行抽象。当前形状已经清晰、局部、不太可能增长时，优先无趣的代码。对只增加间接层、却不消除分支、重复规则、无效状态或生命周期风险的抽象保持怀疑。

跳过这一步的信号：一个新功能让既有的 if/else 链又长出一个分支，或出现第二个必须与第一个保持同步的布尔值。时间分解是另一个信号：按阶段命名的模块会把相同的领域规则在步骤间重复。

## 决策例子

验证通过必须携带版本与证据，不只是 done=true。

## 应用证据

读取本文件后，指出它改变的具体决定和产物。没有改变决定时不列为已应用。当前授权、宿主权限和项目强制门禁始终有效。
