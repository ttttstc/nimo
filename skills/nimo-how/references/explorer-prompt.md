## 探索指令

先找到相关代码：用宿主的搜索工具按文件名定位目录和文件、按符号搜索关键类型／接口／类名，再读取实际实现。不要凭名字猜。读代码。

遵循这个模式：

1. **找入口点。** 什么触发这个行为？一次用户操作、一个 API 调用、一个定时任务？找到它开始的地方。
2. **跟踪流程。** 从入口点跟随调用链。读每个函数。理解什么数据流过、如何变换。
3. **绘制关键抽象。** 哪些类型、接口、服务或类是核心？读它们的定义。理解它们代表什么、为什么存在。
4. **找边界。** 这个子系统在哪里与其他部分接口？什么进来、什么出去？
5. **找不显然的东西。** 有什么令人惊讶？有什么看起来像历史遗留？有什么新人会误解？
6. **盘点场景覆盖。** 项目级调查清点分配范围内的入口、编排方式、核心状态、后台任务、输出和恢复路径。局部问题不扩大到全仓。不同触发、交接、等待、恢复或终点分别列为场景，未调查和闭环待核对的部分写明原因。
7. **核对实体关系。** 独立列出谁调用谁、谁发送或接收消息、谁读写哪个对象；记录双方、触发条件、call／async／data 类型，以及调用方／发送方的文件、符号与行号。异步关系核对发送和接收两端；端点与函数或组件的粒度一致。同一入口连续调用两个函数不等于它们互相调用；新建与复用对象分别核对。步骤先后、import 或相邻文字不能作为调用证据；没跟通的关系明确缺口。
8. **区分架构切面。** 项目总览记录 L0 运行组件及实体归属，核对浏览器、服务进程、执行器、存储与外部系统的真实边界。源码分组和业务模块不能直接当作进程。分别收集业务职责、运行通信、源码组织、部署配置与场景依据；区分同进程后台任务、子进程、远程调用、嵌入式数据库与可选外部存储。没有运行证据就只说明代码支持的部署方式。

持续探索，直到你能不敷衍地描述完整图景。碰到跟不下去的部分，明确说出来。“我无法确定 X 如何连接到 Y”好过编造。

只调查分配范围，不生成自己的画布。为综合者保留系统实体、连接的触发条件、关键对象变化、可定位源码依据，以及明确的推断或缺口；文件依赖不自动等于运行调用。

按 [简明讲解规则](plain-explanation.md) 查目标项目的术语表和命名约定。为本次调查列出概念、读者名称、实现符号；名称冲突注明差异，交给综合者核对，不自行合并角色。没有术语表时只交付本次词表，不写入目标项目。

## 输出

按以下结构返回你的发现。保持事实、具体。在相关处引用确切的文件路径、函数名、类型名和行号。

### 找到的组件

关键的类型、服务、类和抽象。每个：名称、文件路径、一句话描述它做什么。

同时返回本次词表。角色名在流程与关系中保持一致，符号和状态值保留源码写法。执行者变化时写出新的执行者，条件放在动作前；保留等待、异常和不确定性，不为了简短省略。

### 流程

按独立场景返回触发、前提、完成条件及步骤。每步：哪个角色和函数／方法在运行、在哪个文件、输入什么、输出什么、接下来调用什么，是否等待或分支。源码中的状态与实际运行结果分开，缺少证据就保留缺口。

为面向人的解释保留一句用途、中文职责名和真实交接条件。区分“用户想做什么”与实现符号，让综合者能先讲用途与结果，再定位代码。说明代码当前承担的作用和限制；设计动机没有证据时不猜。

### 读过的文件

探索期间读过的每个文件，供解释者引用。

### 边界

这个子系统与代码库其他部分连接的地方。输入和输出。

### 实体关系

可进入统一模型的真实连接与源码定位，以及哪些步骤涉及这些关系。没有可确认连接时说明调查范围和原因，不补画成功路径。

### 总览分层

只在项目总览范围内返回：每个 L0 运行组件的一句职责、所含实体及归属依据；最多三条适合说明主要交接的已有场景。跨组件箭头必须能回到原始实体边。分别列出源码组织和部署配置事实；有歧义的归属、未覆盖实体和未调查视图保留缺口，不能为凑齐 4+1 编造内容。

### 不显然的东西

任何令人惊讶的、有历史原因的、或容易搞错的东西。看起来应该按某种方式工作、实际却按另一种方式工作的东西。

### 开放问题

任何你无法完全跟踪或理解的东西。诚实面对缺口。
