# 理解系统如何工作

探索代码库并回答“X 如何工作”。默认交付有源码依据的文本讲解，帮助读者沿核心场景理解入口、对象变化、决策、异步交接和结束条件。用户显式要求画布时，再按同一理解生成可展开的导览画布。

调查前读取 [简明讲解规则](references/plain-explanation.md)，查目标项目的术语和命名约定。探索者交付本次词表与事实，解释者沿用名称写清执行者、条件、交接和结果。规则同时用于聊天回答与讲解文字，不修改目标项目的术语文件。

## 委派机制

探索者和解释者使用宿主提供的独立子 Agent／独立上下文，只读调查目标代码。探索者只返回事实、证据和缺口；解释者综合成文本讲解，仅在本次要求画布时再产出统一模型。宿主没有独立上下文能力时，由主 Agent 按相同步骤顺序执行，并明确记录降级。所有委派遵守 [委派纪律](../nimo-mode/references/delegation.md)，不得扩大当前授权。

## 步骤 1：判断复杂度

范围有歧义时，先简短说明当前理解，然后直接开始探索；用户可以随时纠正。

- **简单问题**：单一模块、小工具，或“函数 X 如何工作”这类窄问题。不派探索者，由一个解释者一次完成探索和解释，进入步骤 2b。
- **复杂问题**：跨多个文件或服务的子系统、横切功能，或完整架构总览。先并行探索，再交给解释者综合，进入步骤 2a。

拿不准时优先走简单路径。

图与范围跟随问题与用户要求：内联图只画当前问题需要的部分，不为局部问题扫描全仓。用户显式要求画布时才生成画布产物；用户说“只要文字”或禁止写入时，只返回文本与内联图。普通只读调查允许按需生成本次画布产物，不允许修改目标代码、知识页或全局配置。

项目级问题先盘点真实入口、编排方式、核心对象与状态、队列／后台任务、输出与恢复路径，再按职责或用户目标分组。场景数量由源码决定，不能用一两条成功主线代表整个工程，也不套固定数量或示例项目的目录。触发、参与者交接、等待条件、恢复方式或结束条件不同，应分成独立场景。与当前范围相关但尚未调查、闭环待核对或明确排除的场景保留可见条目与原因；范围必需项不能自动标为排除。

同时调查实体之间的调用、异步交接与数据关系。步骤先后是讲解顺序，不等于实体调用；不能用相邻步骤、import 或共同出现来补关系。每条已核对关系都保留调用方／发送方的可定位源码依据。生成画布时把关系写入 `edges`，将每步实际涉及的关系列入 `edgeIds`，依据放在对应节点的 `sources`。工程有实体但缺少关系调查时，说明缺口，不把对象清单或步骤时间线称为完整架构图。

要求画布且已有画布时，先按 [画布合同](references/canvas.md) 检查源码快照。只有 `MATCH` 才复用已经核对的事实；`STALE` 或 `UNKNOWN` 重新调查受影响范围，不用旧模型静默生成新报告。

## 步骤 2a：并行探索（仅复杂问题）

把问题拆成 2 到 4 个互相区分的探索角度，每个角度负责子系统的一个切面。一次性派出全部探索者；宿主不支持并行时，按委派纪律顺序执行并保持上下文隔离。

每个探索者使用 `references/explorer-prompt.md`，并拿到自己的探索角度。要求：

- 从相关目录、关键类型、接口和入口开始搜索。
- 沿真实调用链追踪调用者、被调用者、数据流和类型定义。
- 阅读实际代码，不根据文件名猜测。
- 直到可以完整说明从输入到输出、或从触发到效果的路径再停止。
- 返回场景清单与覆盖缺口；每步记录执行角色、输入、输出、等待／分支，以及场景前提和完成条件。
- 记录新人容易误解的非显然行为。

探索者返回结构化发现：关键组件、运行流程、读过的文件和非显然点。随后进入步骤 3。

## 步骤 2b：直接解释（简单问题）

派一个只读解释者，一次完成探索和解释。使用 `references/explainer-prompt.md`，不提供探索者发现部分。

随后进入步骤 4。

## 步骤 3：综合（仅复杂问题）

所有探索者返回后，派一个只读解释者，把全部发现综合成一份连贯说明。使用 `references/explainer-prompt.md`，填入所有探索结果。

解释者负责消除重复、处理矛盾，产出连贯的文本讲解。仅当本次要求画布时，再按 [画布合同](references/canvas.md) 整合统一模型：系统节点与导览步骤分离，同一步可关联多个节点和连线，同一节点可被多个场景复用。未确认连接和推断单独标注，不把 import 关系、状态名字或缺失日志当作真实执行证据。

生成画布时，统一模型同时承载总览职责、核心对象、场景目录和步骤信息，使用 v2 合同，不另造 UI 旁路数据。项目总览增加 L0 运行组件：显式记录哪些实体属于网页、服务、执行器、存储或其他真实协作方，再从已有实体边聚合跨组件关系；职责分组不是执行环境，不能直接当作进程或机器。场景“已核对”只表示源码链路已核对，不能暗示运行验收已通过；缺少终点或恢复证据时标为待核对，并写明原因。

## 步骤 4：呈现

1. 默认交付文本讲解，含内联 Mermaid 或 ASCII 图说明流程。默认不建模型、不写盘、不运行生成器。
2. 仅当用户显式要求画布（如“生成画布”“要导览图”“画布”）时，才将统一模型保存为当前工作区 `.nimo/how/<scope-id>.input.json`，按 [生成与检查命令](references/canvas.md#生成与复用) 发布。不要临时手写另一套 HTML 或前端项目。
3. 生成成功后返回命令报告的 `modelPath` 和 `htmlPath`。面向用户的调用，用宿主实际支持的文件预览或浏览器打开；无法打开时返回绝对路径链接及原因。内部调用同样交付模型和画布路径，由外层统一展示，不重复打开窗口。
4. 要求画布但环境缺少 Node／文件输出能力时，保留文本与内联图，并明确画布未生成及原因。能力不足不伪装生成成功，不自动安装依赖。
5. 后续画布追问在同一模型中定位节点或导览步骤；只有新增事实或源码变化才更新模型。不能读取用户的画布操作时，不假定知道其当前选择。

画布阅读、成图与总览／场景细则见 [画布合同](references/canvas.md)，仅在生成画布时适用。

面向第一次接触项目的开发者写内容：先说用途和结果，再解释过程，一段回答一个问题。场景标题写“任务交给谁执行？”这类用户问题，步骤说明系统动作，不写成读者操作命令。角色沿用本次词表，精确函数和路径留在实现依据。内联图只画能帮助回答当前问题的真实交接。说明现有设计的作用与限制，不编造作者的设计动机。发布前按简明讲解规则自检名称、交接条件和事实保全。

解释沿用下方结构。可以为了清晰度轻度编辑，不改变已核对事实和未确认项。

## 输出结构

按问题需要保留下列部分，不要求每次全部出现：

- **概述**：它是什么、解决什么问题，以及主要边界。
- **关键概念**：理解后续流程所需的核心类型、服务或抽象。
- **运行机制**：从触发开始，说明关键步骤、数据流向和决策点，并给出可继续阅读的文件与符号。
- **代码位置**：开始维护这个区域所需的最小文件／目录地图。
- **易踩坑点**：非显然行为、特殊约束和容易误判的地方。
- **画布**（仅在生成画布时）：可打开的绝对路径、源码快照与调查范围；用所选场景的步骤解释运行机制。
- **覆盖与缺口**：本次范围内有哪些场景、哪些待核对或未调查、原因是什么；不要宣称仅认识部分场景就完整理解工程。

`nimo-how` 只负责理解当前系统如何工作。画布（按需生成）是静态源码模型，不查询业务运行 ID，不采集实时状态，不成为验证结论来源。用户要对现有设计做对抗性审查或寻找问题时，使用 [nimo-interrogate](../nimo-interrogate/SKILL.md)；要调查“为什么当初这样设计”，使用 [nimo-why](../nimo-why/SKILL.md)。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。交付具体结论、证据、未确认项及原因，不能用 Skill 名称列表代替成果。
