# 理解系统如何工作

探索代码库并回答“X 如何工作”。解释和画布来自同一理解模型，帮助读者沿核心场景理解入口、对象变化、决策、异步交接和结束条件。

## 委派机制

探索者和解释者使用宿主提供的独立子 Agent／独立上下文，只读调查目标代码。探索者只返回事实、证据和缺口；解释者综合模型，由调用者统一发布一个画布。宿主没有独立上下文能力时，由主 Agent 按相同步骤顺序执行，并明确记录降级。所有委派遵守 [委派纪律](../nimo-mode/references/delegation.md)，不得扩大当前授权。

## 步骤 1：判断复杂度

范围有歧义时，先简短说明当前理解，然后直接开始探索；用户可以随时纠正。

- **简单问题**：单一模块、小工具，或“函数 X 如何工作”这类窄问题。不派探索者，由一个解释者一次完成探索和解释，进入步骤 2b。
- **复杂问题**：跨多个文件或服务的子系统、横切功能，或完整架构总览。先并行探索，再交给解释者综合，进入步骤 2a。

拿不准时优先走简单路径。

图范围跟随问题：函数问题交付局部图，跨组件流程交付场景图，项目上手交付系统底图及核心导览。不为局部问题扫描全仓。用户说“只要文字”“不要生成文件”或明确禁止写入时，只返回内联解释与必要图示；普通只读调查允许生成本次解释产物，不允许修改目标代码、知识页或全局配置。

已有画布时，先按 [画布合同](references/canvas.md) 检查源码快照。只有 `MATCH` 才复用已经核对的事实；`STALE` 或 `UNKNOWN` 重新调查受影响范围，不用旧模型静默生成新报告。

## 步骤 2a：并行探索（仅复杂问题）

把问题拆成 2～4 个互相区分的探索角度，每个角度负责子系统的一个切面。一次性派出全部探索者；宿主不支持并行时，按委派纪律顺序执行并保持上下文隔离。

每个探索者使用 `references/explorer-prompt.md`，并拿到自己的探索角度。要求：

- 从相关目录、关键类型、接口和入口开始搜索。
- 沿真实调用链追踪调用者、被调用者、数据流和类型定义。
- 阅读实际代码，不根据文件名猜测。
- 直到可以完整说明从输入到输出、或从触发到效果的路径再停止。
- 记录新人容易误解的非显然行为。

探索者返回结构化发现：关键组件、运行流程、读过的文件和非显然点。随后进入步骤 3。

## 步骤 2b：直接解释（简单问题）

派一个只读解释者，一次完成探索和解释。使用 `references/explainer-prompt.md`，不提供探索者发现部分。

随后进入步骤 4。

## 步骤 3：综合（仅复杂问题）

所有探索者返回后，派一个只读解释者，把全部发现综合成一份连贯说明。使用 `references/explainer-prompt.md`，填入所有探索结果。

解释者负责消除重复、处理矛盾，并按 [画布合同](references/canvas.md) 整合统一模型。系统节点与导览步骤分离：同一步可关联多个节点和连线，同一节点可被多个场景复用。未确认连接和推断单独标注，不把 import 关系、状态名字或缺失日志当作真实执行证据。

## 步骤 4：呈现

1. 默认同时交付解释与画布，无需用户提到“画布”或记住模式。将统一模型保存为当前工作区 `.nimo/how/<scope-id>.input.json`，按 [生成与检查命令](references/canvas.md#生成与复用) 发布。不要临时手写另一套 HTML 或前端项目。
2. 生成成功后返回命令报告的 `modelPath` 和 `htmlPath`。面向用户的调用，用宿主实际支持的文件预览或浏览器打开；无法打开时返回绝对路径链接及原因。内部调用同样交付模型和画布路径，由外层统一展示，不重复打开窗口。
3. 后续问题在同一模型中定位节点或导览步骤；只有新增事实或源码变化才更新模型。可通过画布 URL 的定位参数打开相关区域。不能读取用户的画布操作时，不假定知道其当前选择。
4. 用户要求不生成文件，或环境缺少 Node／文件输出能力时，保留解释和内联图，并明确画布未生成及原因。能力不足不伪装生成成功，不自动安装依赖。

解释沿用下方结构。可以为了清晰度轻度编辑，不改变模型事实和未确认项。

## 输出结构

按问题需要保留下列部分，不要求每次全部出现：

- **概述**：它是什么、解决什么问题，以及主要边界。
- **关键概念**：理解后续流程所需的核心类型、服务或抽象。
- **运行机制**：从触发开始，说明关键步骤、数据流向和决策点，并给出可继续阅读的文件与符号。
- **代码位置**：开始维护这个区域所需的最小文件／目录地图。
- **易踩坑点**：非显然行为、特殊约束和容易误判的地方。
- **画布**：可打开的绝对路径、源码快照与调查范围；用所选场景的步骤解释运行机制。

`nimo-how` 只负责理解当前系统如何工作。画布是静态源码模型，不查询业务运行 ID，不采集实时状态，不成为验证结论来源。用户要对现有设计做对抗性审查或寻找问题时，使用 [nimo-interrogate](../nimo-interrogate/SKILL.md)；要调查“为什么当初这样设计”，使用 [nimo-why](../nimo-why/SKILL.md)。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。交付具体结论、证据、未确认项及原因，不能用 Skill 名称列表代替成果。
