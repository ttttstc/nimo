# How（理解系统如何工作）

探索代码库，回答“X 是如何工作的？”这类问题。产出清晰的架构解释，达到资深工程师 onboard 一个子系统所需的水平：足以建立可用的心智模型，而不是带注释的源代码。

两种模式：

1. **Explain（解释，默认）**。探索代码库并产出清晰的解释。
2. **Critique（审视）**。先解释，再派出多个模型独立识别架构问题。

## 委派机制

本 Skill 的探索者、解释者、评审者都用宿主提供的独立子 Agent／独立上下文派发；宿主无独立上下文时诚实降级：主 Agent 顺序扮演各角色，并明确记录降级，降级下的评审不称独立审查。所有派发遵守 [委派纪律](../nimo-mode/references/delegation.md)；全部角色只读调查，不扩大权限。

## Explain 模式

### 步骤 1：理解问题并评估复杂度

解析用户在问什么：

- “限流器是怎么工作的？”，一个子系统
- “按需用量是怎么计费的？”，一条功能流程
- “auth 服务是什么结构？”，一份架构总览
- “带我走一遍用户提交表单时会发生什么”，一次运行时跟踪

确定范围。有歧义时，先说明你的最佳猜测，再开始探索。不要反问。偏了用户会纠正。

**评估复杂度以决定路径：**

- **简单**（单一模块、一个小工具、像“函数 X 怎么工作”这样的窄问题）：跳过探索者，解释者一遍完成探索与解释。走步骤 2b。
- **复杂**（跨多个文件／服务的子系统、一条横切功能、一份完整架构总览）：先并行派出探索者，再交给解释者。走步骤 2a。

拿不准时按简单处理。解释者撞墙时，随时可以再派探索者。

### 步骤 2a：探索（仅复杂问题）

把问题分解为 2-4 个并行探索角度，每个角度是子系统的一个独立切面，让探索者之间不重复劳动。以“限流器是怎么工作的”为例：

- 探索者 1：数据模型与状态管理
- 探索者 2：请求路径与执行
- 探索者 3：配置与指标基础设施

正确的分解取决于问题本身，自行判断。窄问题：2 个探索者就够。宽子系统：最多 4 个。

一次性并行派发全部探索者（宿主不支持并行时，按委派纪律串行派发，保持各自独立上下文）：

- 派发方式：宿主提供的独立子 Agent／独立上下文，只读授权
- 模型：用户配置的探索用模型；未配置时用宿主当前模型

每个探索者拿到 `references/explorer-prompt.md` 的同一份基础提示词，外加指明其切面的具体探索角度。每个探索者应该：

- 从宽处入手：搜索相关目录，搜索关键类型／接口／类名
- 跟线索走：从入口点跟踪调用链（调用者、被调用者、数据流、类型定义）
- 读实际代码，不凭文件名猜
- 在能不敷衍地描述从输入到输出（或从触发到效果）的完整路径之前不要停
- 记下令人惊讶的、不显然的、新人会搞错的东西

每个探索者返回结构化发现：找到的组件、跟踪到的流程、读过的文件、一切不显然的东西。探索者之间有重叠没关系，解释者负责调和。

然后进入步骤 3。

### 步骤 2b：直接解释（简单问题）

派一个单独的子 Agent，一遍完成探索与解释：

- 派发方式：宿主提供的独立子 Agent／独立上下文，只读授权
- 模型：用户配置的解释用模型；未配置时用宿主当前模型

该 Agent 自行探索（搜索、读代码）并直接写出解释。读 `references/explainer-prompt.md` 获取沟通风格与输出格式。同样的结构，只是没有探索者发现作为输入。

进入步骤 4。

### 步骤 3：综合（仅复杂问题）

全部探索者返回后，派一个单独的子 Agent，把它们的发现综合成一份连贯的解释：

- 派发方式：宿主提供的独立子 Agent／独立上下文，只读授权
- 模型：用户配置的解释用模型；未配置时用宿主当前模型

解释者拿到全部探索者发现，撰写面向人的解释（输出格式见下）。读 `references/explainer-prompt.md` 获取完整提示词模板。解释者调和重叠的发现、解决矛盾，把各个切面编织成统一的图景。

### 步骤 4：呈现

把解释者的输出呈现给用户。可以为清晰做轻度编辑，或补充对话中的上下文，但不要实质性重写。解释者的沟通就是产品。

### 输出格式

遵循这个结构，按问题调整。不是每个问题都需要每个小节。

**概述。** 1-2 段。它是什么、做什么、为什么存在。足以让读者决定是否继续读。

**关键概念。** 重要的类型、服务或抽象。每个一条简短定义。不求穷尽，只列理解其余内容所需的部分。

**运行机制。** 解释的核心。走一遍流程：什么触发它、一步步发生什么、数据去哪、决策点在哪。散文，不用伪代码。引用具体文件和函数让读者可以去看，但不要倾倒代码块，除非某个片段真的必要。

**位置。** 相关文件／目录的简短地图。不是每个文件，只列在这个区域开始工作所需的部分。

**易错点。** 会绊倒人的不显然或令人惊讶的东西。解释某物为什么长得奇怪的历史背景。已知的锋利边缘。

## Critique 模式

当用户要的是架构问题、毛病或改进，而不只是理解时触发。

### 步骤 1：先解释

完整执行上面的解释流程（步骤 1-4）。评审架构之前必须先理解它。

### 步骤 2：派出评审者

解释完成后，为用户配置的评审模型列表中的每个模型各派一名架构评审者；用户未配置时，用宿主当前模型派一名评审者，宿主只有一种模型时用同模型的独立上下文并报告缺少跨模型多样性。全部评审者一次性并行派发（宿主不支持并行时按委派纪律串行派发，保持独立上下文）。

对每名评审者：

- 派发方式：宿主提供的独立子 Agent／独立上下文，只读授权
- 模型：用户配置的评审模型之一。这些是最低推理档位；当架构值得更深入的分析时，主 Agent 应把评审者升级到用户配置范围内更强的模型。

读 `references/critic-prompt.md` 获取提示词模板。每名评审者拿到：

1. 步骤 1 的解释（这样他们不用重新探索）
2. 相关文件路径（这样他们可以读实际代码）
3. `references/critique-rubric.md` 的架构评审标准

### 步骤 3：主 Agent 裁决

与 nimo-interrogate 相同的框架。你是务实的负责人，不是汇总器。

把发现分类：

- **处理。** 值得现在就修的架构问题
- **考虑。** 真实关切，但成本／收益不明
- **记录。** 有效观察，低优先级
- **驳回。** 错误的、缺上下文的、或风格偏好

先呈现解释（来自步骤 1），审视结论放在其后。解释应当独立成立：只想理解系统的人不该被迫蹚过评审内容。
