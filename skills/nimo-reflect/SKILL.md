# 反思

从当前对话里挖出能长期用的教训，再逐条路由到一个具体的技能改动。

触发：用户说「反思」「reflect」「这次学到了什么」。会话琐碎、跑题，或者已经有技能覆盖且父级照做了，就不跑。一次性的偶发不算教训。

## 一、定位这次会话的记录

- 会话记录由宿主提供；先确认它能不能读、在哪。读不到就用这份对话的紧致摘要代替，并说明用的是摘要而不是原始记录。
- 只读当前这次会话，绝不跨工作区去翻别的项目的对话。
- 判断记录是否对得上：开头那条用户原话必须能对上。

## 二、三个视角并行评审

三个视角各审一遍同一份材料，互不通气：

| 视角 | 看什么 |
| --- | --- |
| 判断 | 哪里该停没停、该问没问、该证没证；结论与证据是否对得上 |
| 工具 | 哪一步用手工做了本可脚本化的事、哪个命令白跑、哪个接入没被用上 |
| 发散 | 有没有更省的路径、本该更早发现的信号、被忽略的替代方案 |

- 每个评审者都要给出：问题、证据（指到具体位置或原话）、建议落到哪个技能、改动大概是什么。
- 模型由宿主选。宿主只有一个模型时，用同模型的三个独立上下文，并在结果里注明「同模型，不是跨模型复核」。
- 宿主不能开子 agent 时，由主线程分三次、按同一份材料分别扮演三个视角，并明确写「未做独立并行评审」。

## 三、合成

一次合成，输出三张清单：

- **采纳**：证据站得住、可复用、落在具体技能上。
- **驳回**：证据不足、一次性偶发、或技能已经覆盖且父级照做了。
- **待办**：方向对但这次不改，或需要更大改动。

合成时可以回查引用是否真在那里。查不到就降级为待办，并写明原因。

## 四、结构强制检查

能写成检查脚本、lint 规则、元数据或运行时校验的，一律从「采纳」移到「待办」。改一个技能只是提醒下一个模型注意，写进结构才是真的不再犯。判据见 `nimo-principle-encode-lessons-in-structure`。

## 五、改之前必须经人批准

- 先把合成的三张清单完整给用户看，等他明确批准哪些才动手。技能改动会影响以后每一次运行，不自动落。
- 他可能只批一部分、也可能改路由，按他的选择执行。
- 待办的条目记录下来即可，不自动开 issue、不自动提交；本仓库没有约定跟踪器，开单由用户决定。

## 六、按路由改

- **小事**：一行清单项、一句收紧、一个过期事实的更正，由主线程直接改。
- **实质改动**（新章节、新判据表、十行以上）：交给 `nimo-skill-author`，走它的起草、验证、迭代。
- **技能该触发却没触发**：同样是 `nimo-skill-author`，专门改描述。
- **新技能**：交给 `nimo-skill-author`，不要临时凑形状。
- 改完跑 `node tests/assets/check-package.mjs` 与 `node tests/run.mjs`，报错就修；不许为了让检查通过而删判据。

## 七、向用户交代

短清单，不要开场白：

- 已改：`<技能路径>`，每行一句改了什么。
- 新建：`<技能路径>`，每行一句（很少发生）。
- 待办：`<条目>`，每行一句。
- 丢掉的：每条驳回一个理由。

## 边界

- 不改生产代码，只改技能与其参考文件。
- 不开 PR、不推送；提交与合并由用户决定。
- 与 `nimo-correct` 的分工：correct 处理「同一类纠正反复出现、要落成仓库约束」，面向任务过程；本技能处理「这次对话本身能提炼出什么技能改动」，面向技能库。
- 与 `nimo-skill-evaluate` 的分工：evaluate 判一个技能值不值得留，本技能产出改动建议。
