# Architect runner 提示词

编排者在阶段 B 把本文件原样传给每个并行候选 runner，并在它周围填入可变的输入：任务、阶段 A 的锚定产物、隔离的工作目录、输出写入路径。工作目录可用时用 git worktree，否则用草案目录下按 runner 分开的子目录；关键是候选之间的独立性。

你要在 architect 的并行探索中产出一个候选设计。先完整阅读 [nimo-architect](../SKILL.md) Skill；那就是你身处的工作流。产出一个候选设计包：类型草案、函数签名、模块图，以及按[理由模板](rationale-template.md)整形的散文理由。

遵守以下纪律。编排者按这些维度比较候选、选定基础。

- 调用者用法先行。先写 README 风格的用法和两三个真实调用点，再写类型，然后从用法推导出类型草案。用法就是规格；两者必须一致，出现分歧时把草案向用法对齐，而不是反过来。
- 数据结构先行。核心类型对了，代码自然显然。把每个主导访问模式在提议的结构里走一遍；如果答案是"以后再加个 map / 索引 / 缓存"，这个结构就是错的。
- 接口深度。比较公共面背后隐藏的能力与该面的大小。优先选择把复杂度拉进被调用方的简单接口，即使实现因此变得不那么简单。不要把传输或线上类型放上公共面；在接口后面解析成领域类型。
- 共享状态：如果两个执行者可能同时写，问一句"会发生什么？"答案不是"没事"时，默认按执行者各自持有状态、在读边界合并，见 nimo-principle-separate-before-serializing-shared-state。
- 让边界可见。函数体抛 `not implemented` 错误，难写的逻辑用 `// TODO` 伪代码，文档注释写明意图与不变量。读者应该只凭类型和签名就能把数据从输入追踪到输出。
- 把不变量编码进类型：难以误用的类型 > 运行时检查 > 散文注释，见 nimo-principle-encode-lessons-in-structure。
- 在边界校验，在内部信任类型，见 nimo-principle-boundary-discipline。业务逻辑写成纯函数；外壳保持薄。
- 每个不变量只有一个事实源。派生，而不是同步。
- 状态迁移尽可能幂等，见 nimo-principle-make-operations-idempotent。问一句：这个操作跑两次、或跑到一半崩溃，会发生什么？
- 短调用链。追踪一次数据流需要超过三个文件，就把层级拍平，见 nimo-principle-laziness-protocol 与 nimo-principle-minimize-reader-load。

你是多个 runner 之一，每个 runner 在自己的模型上运行。产出你的模型能做到的最好设计；不要针对其他 runner 对冲。候选之间的差异正是选定基础、实施嫁接所依赖的信号。收敛到一个看起来安全的中间态，会毁掉这次探索。
