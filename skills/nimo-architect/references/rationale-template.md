# 理由模板

随类型草案一起交付的散文。一页以内。标题简洁，不写套话。把斜体提示替换成实际内容。

## 问题

*一段话。我们要做什么；现有系统或约束中的什么，让这个形状不那么显然。如果[阶段 A](../SKILL.md)浮出了设计必须遵守的约束（需要互操作的既有类型、不能破坏的调用者、跨过边界的不变量），在这里点名，让读者看到和你看到的同一批约束。*

## 用法（调用者视角）

*最先写这一节，在类型草案之前。展示消费者会读到的 README 或快速上手，加上他们自己代码里的两三个真实调用点。导入什么、调用什么、返回什么。[形态](#形态)一节里的类型草案由本节推导。两者必须一致；出现分歧时，把草案向用法对齐，而不是反过来。调用者的体验就是规格，类型为它服务。*

## 形态

*推荐的架构。数据结构先行；然后是数据如何流过这些签名。点名承重的决策。说明哪些不变量编码进了类型、校验逻辑放在哪里、系统刻意不做什么。显式判定接口深度：公共面隐藏了什么复杂度、暴露给调用者什么、为什么接口不需要更大。每条决策标注所依据的原则（如"依据 boundary-discipline"）；不要复述原则本身。*

## 综合决策

*由 [nimo-arena](../../nimo-arena/SKILL.md) 填写。记录哪个候选成为基础、为什么；从其他每个候选各自改编了什么；拒绝了什么、为什么。*

## 接受的取舍

*选定形状做出的每个取舍一条。格式："我们接受 X，以换取 Y。"任何未来读者可能误当成疏忽的东西都要点名，包括那些看起来像过早优化或过早简化的东西。*

## 考虑过的备选

*必填。至少给出一个具体的备选形状，加一行说明它为什么落选。按接口深度评判每个备选，而不是只看实现的简单性。说出它暴露给调用者的复杂度和它隐藏的复杂度。设计空间存在真实竞争者时，这里应有两三个备选。约束已经逼出唯一答案时，一个也够，结论写成"这是唯一可行的形状，因为……"。不要罗列同一形状的口味变体。本节写的是选定形状考虑过并拒绝的设计备选，不是其他 runner 候选。*

## 开放问题与风险

*草案期间注意到的、需要人来权衡的事，以及实现开始前值得标记的风险。写成问题而不是断言，让人给出的回答成为结论本身，而不是一条评论。*

## 下一步实现

*对着草案要构建的第一件事。一句话。综合完成（或加入检查点时、阶段 D 签字通过）后，你会立即开始写什么。*
