# 只设计，不实现

先确定结构，再交给实现者填充。用伪代码和接口草案草拟类型、函数签名、类结构与模块边界；从多个候选方案中综合出一个设计，交付给调用者。实现由调用它的 Playbook／实现 Agent 承担。实现过程中发现设计错误时，由实现方带着新的事实重新调用本 Skill，而不是本 Skill 自己长期持有“设计 → 实现 → 重设计”的完整生命周期。

## 开始

开始之前，按阶段建立任务清单，每阶段一条：

1. 建立事实基础
2. 设计草案
3. 确认
4. 输出最终设计

## 阶段 A：建立事实基础

对新代码会触及的每个系统建立真实的工作模型。对相关子系统运行 [nimo-how](../nimo-how/SKILL.md)。

只列出文件名不算理解系统。要产出 nimo-how 要求的、沿真实代码路径追踪得到的模型。如果新设计会改变职责归属或分层，还要对现有结构运行 [nimo-why](../nimo-why/SKILL.md)，让历史设计理由成为约束，而不是靠猜测补齐。

只有真正的全新系统、且没有任何现有系统需要集成时，才跳过阶段 A。

## 阶段 B：形成设计草案

带着设计任务和阶段 A 的事实基础运行 [nimo-arena](../nimo-arena/SKILL.md)。将 [runner 提示词](references/runner-prompt.md)交给每个候选执行者。每个候选按[理由模板](references/rationale-template.md)产出设计包：先写调用者如何使用，再给出类型草案、函数签名、模块图，以及由这些结构推导出的设计理由。

使用用户配置的 architect runners；宿主能使用多个模型时，优先让不同模型家族各产出一个候选。仅有单模型时按委派纪律降级并记录。

至少拿到两个**整体结构明显不同**的候选后才能综合，即使第一个候选已经看起来足够好。这是 nimo-principle-exhaust-the-design-space 的具体应用。需要比较的是整体架构方案，不是在同一个方案里换几个局部细节。

综合前，用[设计风险清单](references/design-red-flags.md)逐项检查每个候选。浅层抽象、内部信息泄漏、按执行时序而不是职责拆模块、只做透传的方法，都应修订或淘汰。

比较可行候选时关注接口深度：优先选择用更小、更简单的公共接口隐藏更多内部复杂度的方案。能力集中在少数高价值接口里，通常比把同一能力拆散到多层调用链更容易维护。

arena 最终返回一个综合设计包，并把选择理由写入理由模板的“综合决策”部分。

## 阶段 C：确认（按需启用）

默认直接交付综合设计，不设置人工检查点。

只有调用方明确要求“实现前停下来确认”“带检查点运行”或同等表达时，才展示综合设计并等待确认。

无论是否设置检查点，综合设计都是交给调用者的独立设计交付物，这是 nimo-principle-foundational-thinking 的“先搭稳定结构，再填实现”。需要在交付前对设计施加对抗性压力时，对综合草案运行 [nimo-interrogate](../nimo-interrogate/SKILL.md)。

如果用户对设计结构提出异议，把它当作阶段 A 的新证据。先重新理解约束，再重跑阶段 B，不要在有争议的结构上继续。

## 阶段 D：输出最终设计

交付物是设计，不是实现。可以输出：调用者使用方式、类型设计、函数签名、模块边界、模块图、数据模型、设计理由、备选方案、风险与实现约束；可以用 `not implemented` 函数体和伪代码表达接口草案。

默认不修改生产实现代码，不把骨架写进正式源码，不承担 Feature / Bug Fix 的实现阶段。调用者要“设计并实现”时，由 Feature / Bug Fix / Refactoring 等上层 Playbook 组合 `architect → implement`，本 Skill 保持单一职责。

## 重新调用的信号

实现过程中出现下列重复模式时，实现 Agent／上层 Playbook 对已实现部分重新运行 [nimo-how](../nimo-how/SKILL.md)，把实现阶段学到的事实带回设计输入，重新调用本 Skill：

- 同一种 workaround 在互不相关的代码里反复出现。
- 多个无关边界情况都需要专门分支才能成立。
- 类型必须依赖 `any`、强制转换、实践中总会赋值却被声明为 optional 的字段等方式绕过约束才能编译。
- 草案认为状态不共享，实现却不断出现“需要加锁”的需求。
- 调用方必须理解抽象内部规则才能正确使用它。
- 实现过程中出现两处以上结构相同、彼此独立的草案偏离。

几个孤立边界情况不足以否定整个设计。有些问题本身就复杂；数据和业务复杂，不等于设计结构有问题。真正需要重设计的信号是同一种结构性摩擦反复出现。

重新调用时遵守 nimo-principle-redesign-from-first-principles、nimo-principle-fix-root-causes 与 nimo-principle-subtract-before-you-add：把新增约束当成从第一天就存在的基础条件重新设计；新草案先尝试比旧草案更简单，再考虑增加结构；回到阶段 B 重新运行 arena。

## 输出

先写调用者如何使用，再从使用方式推导类型和接口。小改动交付类型与签名草案；较大的工作交付模块图和类型定义。设计理由随草案一起交付，并按[理由模板](references/rationale-template.md)记录使用方式、备选方案和综合决策。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。默认不修改生产实现代码；交付具体产物、当前版本证据、未完成项及原因。跳过步骤必须记录理由，不能用 Skill 名称列表代替成果。
