# 设计先于实现

先设计，再实现。用 `not implemented` 函数体和伪代码勾勒类型、函数签名、类形状与模块边界。综合多个模型视角，然后对着选定的草案填充代码。如果实现证明草案错了，扔掉草案重新设计。

## 开始

开始之前，按阶段开一份 todolist，每阶段一条。无检查点的自治运行需要这份清单来显示当前推进到哪个阶段，并防止阶段被悄悄跳过。

1. 锚定
2. 草案
3. 确认
4. 实现
5. 废弃

## 阶段 A：锚定问题

为新代码触碰的每个系统建立真实的心智模型。对相关子系统运行 [nimo-how](../nimo-how/SKILL.md)。当现有结构本身就是约束、或设计必须顶回这个结构时，使用审视模式。

报出一个文件名不叫锚定。要产出 nimo-how 所规定的、经过实际追踪的模型。如果设计会重新定义所有权或分层，还要对现有形状运行 [nimo-why](../nimo-why/SKILL.md)，让既有决策的理由成为新设计的约束，而不是猜测。

只有当工作真正是全新空地、没有任何周边系统需要集成时，才允许跳过阶段 A。

## 阶段 B：草案

带着设计草图任务和阶段 A 的锚定产物运行 [nimo-arena](../nimo-arena/SKILL.md)。把 [runner 提示词](references/runner-prompt.md)作为每个候选 runner 的提示词传入。每个候选产出一个按[理由模板](references/rationale-template.md)整形的设计包：调用者的用法最先写出，然后是类型草案、函数签名、模块图，以及由这些推导出的散文理由。

使用用户配置的 architect runners（宿主可用多个模型时优先不同模型家族各开一个；仅单模型可用时按委派纪律降级并记录）。

把设计做两遍。综合之前必须拿到至少两个结构性不同的候选，即使第一个看起来已经足够。这是 nimo-principle-exhaust-the-design-space 原则 Skill 的具体化。要的是整体形状层面的备选方案，不是一个形状内部的点状修补。

综合之前，用[设计红旗](references/design-red-flags.md)逐条筛查每个候选。浅模块、信息泄漏、时序分解、透传方法，要么修订，要么拒绝。

在接口深度上比较可行候选。优先选择在更小、更简单的公共面背后隐藏更多复杂度的设计。一个能力集中的丰富接口可以保持调用链短，而不是把能力散布到各层。

arena 返回一个综合后的设计包。综合决策填入理由模板的"综合决策"一节。

## 阶段 C：确认（可选加入）

默认：带着综合设计直接进入实现，无人工检查点。

仅当调用方明确要求时才加入检查点："带检查点运行"、"实现前停下来给我看"或类似表述。此时呈现综合设计并暂停等待签字。

无论是否加入检查点，综合结果都可以作为独立提交交付。这是 nimo-principle-foundational-thinking 的"先搭脚手架"模式；后续提交读起来就是在稳定契约下填充函数体。填充期间计划内、已圈定范围的破坏是允许的，见 nimo-principle-outcome-oriented-execution。要在实现前对设计施加对抗性压力，就对综合草案运行 [nimo-interrogate](../nimo-interrogate/SKILL.md)。

如果人对形状提出异议（在检查点上或事后），把它当作阶段 A 的新证据。先重新锚定、重跑阶段 B，再写更多代码。

## 阶段 D：对着草案实现

把 `not implemented` 函数体替换成代码，把伪代码替换成逻辑。综合草案就是契约。

对草案的偏离是值得浮现的信号，不是应该默默吸收的摩擦。如果某个函数需要一个草案没预料到的参数，追问：是草案错了，是需求漏了，还是实现越界了。把它浮现出来；不要硬拴上去。

## 阶段 E：架构错了就废弃

如果实现持续产生草案吸收不了的摩擦，扔掉草案。不要在错误的设计上硬拴补丁，见 nimo-principle-redesign-from-first-principles 与 nimo-principle-fix-root-causes。

触发信号是模式，不是单次事件。征兆：

- 同一种形状的 workaround 在互不相关的代码里反复出现。
- 多个互不相关的边缘情况，全都需要特例分支。
- 类型需要逃生舱（`any`、强制转换、实践中总是被赋值的 optional 字段）才能编译。
- 草案明明说状态不共享，却冒出"我们得加把锁"的反射。
- 调用者必须了解抽象的内部规则才能使用它。
- 实现中出现两处以上同形状的独立阶段 D 偏离。浮现偏离是阶段 D 的职责；偏离的重复模式是阶段 E 的触发器。

运用判断力。几个边缘情况不足以定罪一个架构。有些问题本来就复杂；数据本身的复杂度不等于设计上的复杂度。重写的信号是同形状摩擦的重复，不是单个困难案例。

废弃时：

1. 对已建成的部分重新运行 [nimo-how](../nimo-how/SKILL.md)。实现中的教训作为输入进入新设计，不是凭感觉。
2. 把新约束当作第一天就成立的假设来重新设计，见 nimo-principle-redesign-from-first-principles。
3. 先做减法，见 nimo-principle-subtract-before-you-add。新草案应当先变得比旧的更小，再考虑增长。
4. 回到阶段 B，重跑 arena。

## 输出

调用者的用法最先写出，类型草案由它推导。小改动交付一个包含新类型与签名的文件；较大的工作交付模块图加类型定义。理由随设计一起交付，按[理由模板](references/rationale-template.md)整形，包含用法草案与综合决策。

## 边界与交付

遵守 [宿主合同](../nimo-mode/references/host-contract.md) 和 [委派纪律](../nimo-mode/references/delegation.md)。只读、方案或停止要求优先，步骤不扩大授权。交付具体产物、当前版本证据、未完成项及原因。跳过保留理由，不能用 Skill 名称列表代替成果。
