# 把重复错误变成约束

## 适用

同一纠正或错误反复出现；发现自己第二次写下同一条指令。

把反复出现的修复编码进机制（工具、代码、元数据、自动化），而不是文字指令。每个错误、每次人工纠正、每个意外结果都是学习信号。捕获它、路由它、闭合回路。

## 为什么存在

文字指令容易被漏掉：它要求读者注意到、记住并遵守。结构性机制（lint 规则、元数据标志、运行时检查、自动化脚本）不需要配合就强制执行规则。

## 模式

当你发现自己第二次写同一条指令：

1. 问：它能变成 lint 规则、元数据标志、运行时检查或脚本吗？
2. 能，就编码它，并删除那条指令。
3. 不能（确实需要判断力），就把指令做得更醒目，并附上一个失败模式的例子。

**选择最强的一档。** 多种机制都可行时，选情境允许的最强者（先是让非法状态无法编译，然后是让 CI 失败的 lint 或禁用 API，然后是规范化的辅助函数，最后是运行时检查），因为 Agent 会模仿周围代码已有的做法，较弱的护栏会成为下一个被复制的模板。

## 推论

不要遮盖症状。如果修复是结构性的，就只用结构性修复。那条指令本身就是症状。

## 反馈回路

- **捕获每次纠正。** 人介入或测试失败时，判断它是一次性现象还是模式。
- **路由到正确的层。** 一次性现象 → 当前会话或任务记录。反复出现的修复 → Skill 或 lint 规则。系统性问题 → Principle。写入持久或共享资产受用户当前授权约束。
- **闭合回路。** 不只记录：现在就应用，或创建具体的待办。

## 反模式

- 只承认不记录（"我会记住的"不会持久）
- 只记录不路由（一条"应该存在某个 lint 规则"的记录，除非规则真的落地，否则是浪费）
- 只修复不泛化（修好一个实例，却留下反复出现的模式完好无损）

## 决策例子

无效状态组合用类型禁止，而不是再次口头提醒。

## 应用证据

读取本文件后，指出它改变的具体决定和产物。没有改变决定时不列为已应用。当前授权、宿主权限和项目强制门禁始终有效。
