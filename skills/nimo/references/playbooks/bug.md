# Bug 修复 Playbook

## 适用

可复现或疑似缺陷的修复任务。反馈模糊时先利用功能入口、截图线索、代码和日志查明事实，不把猜测当缺陷。

## 目标

用最小变更修复根因，证据区分修复前失败与修复后结果；不以遮蔽症状代替修复（原则 P4）。

## 进入前所需事实

- 复现路径与观察到的错误行为。
- 受影响的功能或模块位置（有功能地图时先定位条目；无地图时记录未覆盖）。
- 修复的验收行为。

## 推荐步骤

理解反馈 → 定位相关功能地图 → 复现并保留失败证据 → 调查根因 → 实施最小修复 → 验证与回归 → 必要的独立审查 → 交付

委派划分（细则见 `../delegation.md`）：

- **主 Agent 保留**：原始复现、最终验证证据、验收与交付判断。
- **默认委派**：明确范围的调查（独立假设可分片调查）；非简单修复的实现。
- 依赖根因的设计和实现，必须等根因得到证据支持后再启动。

## 必要检查

- 修复前失败证据（可重复）。
- 修复后在**原始操作面**的通过证据：真实界面问题还需在对应界面验证，内部方法测试不能代替用户路径。
- 回归：受影响范围的适用检查。
- 产品行为或入口改变时，核对受影响的功能地图条目。

## 跳过条件（如实标注，不能改写成通过）

- **无法复现**（缺少账号、设备或外部状态）：明确缺少条件，继续不依赖该条件的调查；修复标注未验证。无法复现不等于不存在缺陷。
- **无廉价测试路径**：静态修改不能冒充已验证修复，如实记录验证方式与限制。

## 所需能力

investigate、implement、verify、review（能力合同见 `../capabilities.md`）。

## 交付内容

修复差异、修复前／后证据、回归结果、未验证项与原因。
