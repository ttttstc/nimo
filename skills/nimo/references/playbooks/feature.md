# Feature 开发 Playbook

## 适用

新增或明确改变行为的开发任务。

## 目标

交付满足验收行为的实现；新增入口、状态和副作用进入验证范围。

## 进入前所需事实

- 用户结果与验收行为。
- 现有系统的相关结构与数据流。
- 非简单任务在实现前明确领域数据和状态结构。

## 推荐步骤

明确用户结果与验收行为 → 理解现有系统 → 解决关键设计问题 → 拆分可验证工作 → 实现 → 行为验证 → 必要的独立审查 → 交付

委派划分（细则见 `../delegation.md`）：

- **主 Agent 保留**：设计取舍、验收与交付判断。
- **默认委派**：非简单任务的代码实现。
- 跨边界或存在实质方案竞争时开展设计探索；实质不同的方案按候选比较处理。
- 可以通过廉价实验回答的问题优先验证事实，不先做长篇推演。
- 启动实现前核对共同前提、独立工作、共享状态和最小拆分；共享修改由单一所有者整合。

## 必要检查

- 验收行为在真实产物上通过并留有证据。
- 新增入口、状态和副作用进入受影响的功能地图及验证范围（无地图时记录未覆盖）。
- 整合后的复验：子任务各自通过不表示合并后的产物已通过。

## 跳过条件（如实标注，不能改写成通过）

- 范围小且风险明确：可合并规格和设计步骤，不强制生成独立文档。
- 用户授权跳过非强制检查：如实标注跳过／未验证。

## 所需能力

investigate、specify、design、implement、verify、review（能力合同见 `../capabilities.md`）。

## 交付内容

实现差异、验收行为证据、未验证项与原因。
